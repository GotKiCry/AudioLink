## 1. 对标项目全景

| 项目 | 传输 | 编码 | 发现 | 延迟量级 | 同步方案 | 可借鉴 / 结论 |
|---|---|---|---|---|---|---|
| **Snapcast** | TCP | Opus/FLAC/Vorbis/PCM | Zeroconf | **端到端默认 1000 ms** | NTP 式四时间戳 + 最近 200 样本中位数 + 1 s 周期，**设备间偏差 < 0.2 ms** | ✅ 播放调度公式、时钟同步参数；"同步 ≠ 低延迟"的活证据 |
| **Jamulus** | UDP | 未压缩 PCM/Opus | 手工/目录 | 默认缓冲 26.7 ms | 自适应抖动缓冲 | ✅ **抖动缓冲算法可直接落地**（10 个仿真缓冲 + 误差率阈值） |
| **Airfoil（商业）** | 私有 | AAC | Bonjour | 官方原文：*will delay all playback to match the highest delay required* | 以最慢设备为准 | ✅ 同步策略的取舍参照：宁可整体加延迟，也不让设备错位 |
| **AirPlay 2 / RAOP** | TCP/UDP | ALAC/AAC | Bonjour | 中 | 时钟同步 + 缓冲协商 | 参考其"缓冲协商"思想（本项目用 `lead_ms`/`buffer_ms` 协商替代） |
| **AES67 / PTP** | RTP | L16 | — | sub-µs 同步 | **PTP + 硬件时间戳** | ❌ **不抄**：Android 软终端做不到硬件时间戳；仅采其缓冲经验式（≥ 3×、推荐 20× 包时长） |
| **mkckr0/audio-share** | 私有 TCP | PCM（未压缩） | 手工 | 未公开 | 无 | ✅ **工程规范值得抄**（2.1k★、482 commits、仍在更新、Apache-2.0、C++20 + Asio + protobuf + Android Ktor、默认端口 65530）；❌ 但它同样**未压缩、无多设备同步**，不解决我们的核心问题 |
| **AudioShare / AudioPipe（基线）** | 裸 TCP | PCM16 | UDP 广播（Windows 侧已失效） | 未公开 | 事后 seek 拉平 | ❌ 反面教材；已停更 |

## 2. 直接采用（写进设计）

| # | 结论 | 落点 |
|---|---|---|
| A1 | **播放调度公式**：`age = (本地当前时刻 − 该块目标时刻) − buffer_ms + dac_latency_ms`；`age > 0` 丢弃、`< 0` 补静音后播 | `03-protocol.md` §7.1（接收端播放调度） |
| A2 | **时钟同步参数**：四时间戳法 + 最近 200 样本取中位数 + 1 s 周期 + 首连 50 次快速收敛 | `03-protocol.md` §6 |
| A3 | **抖动缓冲算法**：10 个仿真缓冲（深度 2–11 块）并行记账，取误差率 ≤ 0.0005 的最小深度；不对称 IIR（升慢降快）+ 0.1 块迟滞 | `02-architecture.md` §6 |
| A4 | **缓冲经验式**：安全下限 ≥ 3 × 包时长，高抖动场景按 20 × 预留 | `03-protocol.md` §7.1 |
| A5 | **数据面单播**：RFC 9119 明确 802.11 组播以基础速率发送、无 ACK/无重传、受省电模式影响 | `02-architecture.md` §6 |
| A6 | **协议报文必须版本化 + 长度自描述**（旧版用"魔数 + 固定长度阈值"推断格式，直接导致发现功能失效 100%） | `03-protocol.md` §3、§9 |
| A7 | **工程规范**：协议定义集中（IDL 风格）+ 文档含"防火墙配置 / 权限说明 / 已知问题"三件套（借鉴 mkckr0/audio-share 的文档结构） | `03-protocol.md`、`README.md` |
| A8 | **端到端延迟按档位与 P95/P99 验收**，不与"设备间同步"混为一谈 | `01-requirements.md` §5.1、§6 |

## 3. 明确避免（踩过的坑与会受伤的取舍）

| # | 结论 | 说明 |
|---|---|---|
| B1 | **音乐场景关闭 Opus in-band FEC** | `opus_defines.h` 原文该机制 *only applicable to the LPC layer*；开启会逼编码器走 SILK，损伤音乐 → 改用 **NACK 重传 + PLC**（局域网 RTT < 1 ms 完全来得及）；必须显式设置 `OPUS_SET_PACKET_LOSS_PERC` |
| B2 | **不要为时间戳引入 CRC** | `Snapcast` 全仓库检索 `crc`/`checksum` **零命中**，其时间戳靠 TCP 保完整性 → "CRC 时间戳"是误传，别照抄设计负担 |
| B3 | **不抄 AES67/PTP 级别的同步** | 需硬件时间戳；Android 软终端不可达。ms 级同步 + 时间戳调度即可满足 FR-22 |
| B4 | **数据面绝不用组播** | 见 A5；组播仅用于发现，且必须保留 UDP 广播与手工 IP 兜底 |
| B5 | **不要"发现即连"** | 旧版同网段任何人可推流；改为 PIN 配对 + 白名单（FR-17） |
| B6 | **不要把均值当验收指标** | 上游 issue #7 的教训：Wi-Fi 长尾显著，必须按 P95/P99 设计缓冲与降级策略 |

## 5. 与基线的对照结论（一句话）

> 基线（AudioShare/AudioPipe）在**功能设计**上有可取之处（声道分流、遥控音量、托盘形态），
> 但在**协议工程、延迟控制、多设备同步、安全**四个方面均未达标，且已停更、issue 无人处理。
> AudioLink 的定位不是"修 bug"，而是**重新定义同时具备低延迟（P50 80–110 ms）与严格同步（±10 ms）的局域网音频分发能力**。

## 6. 收官补充（Cluster A 源码级核实，直接影响验收）

### 6.1 Android 侧延迟：差一个数量级，只差几行设置

Oboe 官方实测数据（同机型）：

| 配置 | 输出延迟 |
|---|---|
| LowLatency + Exclusive + 回调 | **~20 ms** |
| **漏设 `LowLatency`** | **~205 ms** |
| **多做一次采样率转换（SRC）** | **~160 ms** |

→ 已固化为两条硬性验收用例：**全链路锁 48 kHz（NFR-13）** 与 **显式 `PERFORMANCE_MODE_LOW_LATENCY`（NFR-14）**。
→ 另注：**Android CDD 只要求输出延迟 ≤45 ms**，因此不能假设所有机型都能做到 10 ms 级；验收需按机型记账。

### 6.2 验收目标（与 §1 的档位并存，不矛盾）

- **设计目标**：A 档 40–55 ms（有线 / 良好 Wi-Fi）。
- **验收线**：**端到端 80–120 ms**（否则会在劣质机型上大面积不达标）。
- **设备间同步**：设计目标 **≤5 ms**，验收线 **≤10 ms**（Google 自定合格线是 20 ms，本项目严格 4 倍）。
- **测量方法**：可采用 Google 开源的 [audio-sync-kit](https://github.com/google/audio-sync-kit) 的测量方法作为验收基线（已在 M3 工具 `sync-measure` 中规划）。

### 6.3 Wi-Fi 组播的致命论据是 DTIM（比"会丢包"更彻底）

RFC 9119：**只要 AP 下任一设备启用省电模式，组播帧就会被 AP 缓冲到下一个 DTIM 才发送**。DTIM 周期（典型 100 ms 量级）把收发时刻量化到 beacon 节奏上，**即使不丢包，播放时刻也无法对齐**。
→ 进一步坐实：**组播绝不能用于同步或数据面**。折中拓扑参考 Sonos：**组播用于发现/控制信令 + 对邻居设备单播直发**。

### 6.4 Snapcast 的 Opus 配置可直接抄

`OPUS_APPLICATION_RESTRICTED_LOWDELAY` + 强制 **48 kHz / 16 bit / 立体声** + **按链路状况退化帧长（60/40/20/10 ms）** + 12 字节伪 codec header（`0x4F505553`"OPUS" + samplerate u32 + bitdepth u16 + channels u16，均 LE）。
→ 与 §6.1 结论自洽：**低延迟场景锁死 48 kHz 免重采样 + `RESTRICTED_LOWDELAY`**，已写入 `03-protocol.md` §8。

### 6.5 三处前提纠正（避免我们继续传播错误信息）

| 曾流传的说法 | 核实结论 |
|---|---|
| Snapcast 用 CRC 校验时间戳 | ❌ 全仓库无 CRC 代码；靠 TCP 保完整性 |
| Snapcast 用固定 latency + resampling 做漂移补偿 | ⚠️ 只对一半：固定 latency 成立，但漂移补偿是**均分切片丢/补单帧**（±500 ppm 上限）；`Resampler` 仅用于格式转换 |
| Wi-Fi 组播 + 播放时刻对齐可达 ±1–5 ms | ❌ 查无一手来源（且 DTIM 机制与之矛盾） |
