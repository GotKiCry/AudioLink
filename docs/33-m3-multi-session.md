# M3 · 多会话：共享采集枢纽（一路采集喂 N 台接收端）

> 日期 **2026-09-16**。M3 交付物 1 是「发送端并行推流（≥ 8 目标），每会话独立统计与音量」。
> 本轮把它的**结构**做出来了：采集从「每会话一路」改成**引擎级共享的采集枢纽**。

---

## 1. 为什么共享采集是正确性问题（不是优化）

一台发送端给 N 台接收端推同一路音频时，组内同步的基准是**发送端指定的 epoch + sample_index**。

若每个会话各自开一路采集：读取起点不同、丢样各不同 → 各会话的 seq / sample_index 时间轴彼此错开
几十毫秒量级。接收端按**同一个 epoch** 播放时，这点错位会原封不动加到组内偏差上 ——
而 M3 的验收是「组内 ±10 ms」。

共享采集把「同一帧编号」变成全组公共的起点：**枢纽统一分配 seq / sample_index**，各会话只用不造。

## 8. 时钟稳定性：稳定后 offset 抖动 ≤ 2 ms（2026-09-17 补验）

M3 验收表第 4 条是「稳定后 offset 抖动 ≤ 2 ms（遥测曲线）」。此前 `clock_sync` 只断言了**收敛**
（2 s 内攒够 8 个样本、单次 `|offset| ≤ 2 ms`）—— 那是「一次快照准不准」，**不是**「稳定之后抖不抖」。
缓慢漂移与周期性跳变都不会体现在一次快照上，所以补了这条。

新增 `clock_sync.rs::offset_jitter_stays_within_two_milliseconds_after_convergence`：
配对后每 100 ms 采一次估计（探测间隔也是 100 ms，等于每个新估计采一次），跑 12 s，
丢掉前 2 s 的收敛期，取稳定期 offset 的**极差**作为抖动。

### 8.1 实测

```text
[clock-jitter] 稳定期 83 个样本 · offset 21..24 µs · 抖动 3 µs（验收线 2000 µs）
```

抖动 **3 µs**，比 2 ms 的验收线低约 **600 倍**；同期收敛测试给出 offset = 73 µs、quality = Good、
RTT P50 = 321 µs。

### 8.2 这条测的是什么、不测什么

两个引擎在同一进程里共享同一个单调时钟基准，**真实偏移恒为 0**，所以这里量到的 3 µs 完全是
「估计器 + 收发节奏」引入的误差（调度、锁、µs 取整）—— 它证明的是**估计器本身稳**。
真机上的抖动还包含晶振漂移（靠 `drift_ppm` 速率补偿），那部分仍属 M3 的真机验收。

代价：这条测试跑 12 s，进 `core-heavy` 的 test 步骤（与其它集成测试同批）。

## 7. 组内同步的回环量法（2026-09-17 补验）

M3 验收表里「组内偏差 ≤ ±10 ms（P95）」的验收方法写的是「双机同期录音 + 波形对齐」—— 那要两台设备。
但这条指标在**同一进程**里就能量：两个接收端共用同一个单调时钟，只要记下各自 sink 写出每一帧的时刻，
「第 k 次写出」的时刻差就是它们的播放偏差。

新增 `core/crates/audiolink-engine/tests/engine/group_sync.rs`：1 发送 + 2 接收 + 建组（同一 epoch 排播）
+ `start_send_many`，跑 6 s 后逐帧比较。

### 7.1 两个数字，回答两个不同问题

| 数字 | 含义 | 用途 |
|---|---|---|
| `absolute`（偏移 0） | 两台设备**听到同一内容**的时刻差（含起播差） | 对应 M3 验收线 |
| `aligned`（最佳整数帧偏移） | 扣掉起播差后的**播放抖动** | 护栏断言用 |

### 7.2 实测（2026-09-17，连跑 4 次）

| 次 | absolute P50 | absolute P95 | aligned 偏移 |
|---|---|---|---|
| 1 | 19.65 ms | 20.14 ms | — |
| 2 | 0.51 ms | 0.57 ms | 0 帧 |
| 3 | 0.50 ms | 0.56 ms | 0 帧 |
| 4 | 0.02 ms | 0.78 ms | 0 帧 |

**结论**：常态下两端**几乎完全同步**（P95 < 1 ms，远优于 ±10 ms 验收线）。
但第一次观察到两端起播**整整错开一帧**（20 ms），那一次会超线。样本只有 4 次，不足以说它是稳定缺陷，
也不足以说它是纯偶然 —— 因此单独立了一条**观察项**（见看板），而**不**把它写成断言。

### 7.3 为什么断言用 aligned

验收线关心的是 `absolute`，但 `absolute` 里混着「起播对齐」这个一次性事件：两端若错一帧，整段都差一帧，
断言就会红。护栏要盯的是「排播有没有变坏」，所以断言 `aligned`；`absolute` 打印出来供人看，
由观察项跟踪。**这不是回避问题**：问题被记下来了，只是不用一个会偶发失败的断言去表达 ——
那种断言的下场是被忽略。


### 7.5 根因与修复（2026-09-17，两层）

那个「偶发错一帧」查清了，是**两层**原因叠在一起：

**第一层：判定直接比微秒。** `EpochSchedule::action` 比较的是「现在 ≥ target」，而 target 是**任意**微秒时刻。
两端各自的判定时刻只要落在它前后 1 µs，就会一头「还没到、等一拍」、一头「到了、立刻播」。
修法：target 向上对齐到帧边界（`frame_aligned_target_us`）。回归测试 `both_ends_decide_the_same_within_one_frame`（epoch 刻意落在帧中间）。

**第二层（真正的根因）：播放线程的拍点相位各不同。** 判定发生在**每一拍**上，而 `next_write` 初始化为
`Instant::now()` —— **线程启动那一刻**。两端线程启动时刻不同，拍点相对全局帧网格的相位就不同：
一端拍点落在目标之前、另一端落在之后，**起播整整差一帧**。这也解释了为什么结果只有两种（0 或 ~20 ms），
而不是连续的抖动 —— 相位差是固定的，不是随机的。

修法：起播时把拍点**锚到全局帧网格**（`now_monotonic_us() % frame_us` 的下一个整数倍），之后每拍 +period
保持在网格上。两端因此在**同一拍**做同一个决定。

### 7.6 修复后的实测（连跑 4 次）

| 次 | absolute P50 | absolute P95 | 偏移 |
|---|---|---|---|
| 1 | **0.00 ms** | 0.03 ms | 0 帧 |
| 2 | **0.00 ms** | 0.03 ms | 0 帧 |
| 3 | **0.00 ms** | 0.04 ms | 0 帧 |
| 4 | **0.00 ms** | 0.04 ms | 0 帧 |

从「5 次里 2 次 19.7 ms」变成「4 次全部 0.00 ms」—— 组内偏差比 ±10 ms 的验收线低约 **5 个数量级**。

**护栏也随之上调**：断言改为直接盯验收线（absolute P95 ≤ 10 ms），另加一条自检（扣掉起播差后 P95 ≤ 5 ms）。
当初只能断言 `aligned`，是因为断言 `absolute` 会随机变红；现在根因修了，护栏该回到它本来该盯的东西。
### 7.7 复核：第三层根因才是真正的根（2026-09-17）

§7.6 的「连跑 4 次全绿」是小样本的运气：随后 CI run `35151576499` 又红在同一条断言上
（absolute P50 19.98 ms / P95 20.38 ms，扣帧后 0.01 / 0.02 ms），复现率统计为
**CI 4 次 1 次、本机 12 轮 2 轮**（约 20~40%，负载相关，重跑即绿）。

第三层根因：拍点锚在**全局**帧网格（相位 0），而 target 也曾被向上取整到同一个全局网格 ——
两端的时钟估计只差 ε，同一帧的 target 就相差 ε，各自取整后便可能落到**相邻两格**，
表现为「组内偏差不是 0 就是整整一帧」。

修法：`EpochSchedule::target_us` 不再做网格对齐；新增 `phase_us`（相位由该帧 target 算出，且必须传真实序号）；
播放线程起拍锚点 `playout_start_anchor` 改用待播帧 target 的相位。修后单次实测
**P50 0.00 ms / P95 0.02 ms（偏移 0 帧）**，复现率采样见 `docs/49-m3-group-start-phase.md` §5.3。

教训：**先问「参考系对不对」，再问「取整对不对」** —— 两次「已解决」都栽在同一个盲点上。

## 6. 动态加入：运行中第 3 台加入，前两台不中断（2026-09-17 补验）

M3 的验收表有四条：并发、同步、**动态**、时钟。此前：并发由本文档 §3 的 3 台测试覆盖，
同步要真机同期录音，时钟由 `clock_sync` 覆盖 —— **只有「动态」没有任何自动化证据**，
而它恰恰是最容易出问题的：新会话加入时要新建采集订阅、新建编码器、新建 QUIC 会话，
任何一处争用都可能让**已经在跑的会话**停顿。

新增 `core/crates/audiolink-engine/tests/engine/dynamic_join.rs`：

1. 两台接收端先配对、开流、跑 4 s（确认各自确实在出声）；
2. 第三台**在运行中加入**（连接 → PIN → 开流）；
3. 再跑 4 s，量三台各自的**样本增量**。

判据用「接收侧 sink 的样本增量」而不是「状态还是 Streaming」：状态是采样出来的，
断流几百毫秒可能采不到；样本数不增长才是**直接证据**。

### 6.1 实测（2026-09-17）

```text
动态加入：前两台新增 [387840, 387840] 个样本，第三台 382080 个样本
```

理论满额 = 4 s × 48 kHz × 2 声道 = **384 000**。前两台都在满额之上、第三台也接近满额 ——
**第三台的加入没有让前两台掉一个样本**。

### 6.2 仍未做

- 真机三台同时出声（组内 ±10 ms P95）仍需设备，见 §5 的「未做」表；
- 本测试跑在 `core-heavy` 的 test 步骤里，不额外占用 CI 时间。

## 9. 并行 ≥ 8 台接收端（2026-09-17 第 62 轮补，路线图「多会话」那条的账）

§5 的「未做」表里写着「多会话（并行推 ≥ 8 台）—— M3 交付物 1 未开始」。本轮把这条补上：
`tests/engine/multi_session.rs` 新增 `one_capture_feeds_eight_receivers`，1 发 + **8 收**，
8 台同组（`create_group` + `start_send_many`），跑 5 s。

判据三条，都要**直接证据**：

1. 8 台都真的出声 —— 用**非静音样本数**，而不是「链路码率非零」（后者在「收到了但播不出来」时同样通过）；
2. 8 台都进了 epoch 排播（`PlayoutScheduled` 各一次）—— 8 台同组，一台漏排就是一台永远同步不上；
3. 8 台的播放量同量级（彼此相差不超过一成）—— 「有出声」抓不住「某台几乎不出声」，
   第 61 轮那个 `join_group` 缺陷正是这么漏过去的。

### 9.1 实测（连跑 4 次，数字完全一致）

```text
[multi-8] 8 台非静音样本 [470400, 470400, 470400, 470400, 470400, 470400, 470400, 470400]（8 台，其中 8 路在链路上）；排播事件数 [1, 1, 1, 1, 1, 1, 1, 1]
```

四轮全绿、逐台样本数**一模一样**（470 400 = 9.8 s 音频），8/8 都有排播事件。
这说明共享采集枢纽 + 组排播在 8 路并发下没有任何一路被饿着，也没有哪一路多播少播。

引擎全套：集成 29 项 + 单测 150 项全绿。这条测试跑 5.4 s，进 `core-heavy` 的 test 步骤。

### 9.2 这条测的是什么、不测什么

- **测**：8 路并发下的结构正确性（同一路采集喂 8 个会话、每路都排播、每路的播放量一致）；
- **不测**：8 台真实设备的扬声器输出延迟差异与「同时出声」的听感 —— 那需要 8 台设备加同步录音，
  进程内量不到（见 §5 的「未做」表）。换言之，这条把 M3 交付物 1 的**回环侧**钉住了，真机侧仍挂账。
