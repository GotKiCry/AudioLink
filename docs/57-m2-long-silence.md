## 0. 一句话

「长断音」此前**判不了**，`docs/22` §11.5 把它明确记为遗留；本轮在引擎播放线程里**直接量出**连续静音段
（长度、内容 / 补静音拆分、段内峰值），经**事件**上报、经**快照**可读，**净增 0 个 wire 字段**。

⚠️ **这不是「M2 长断音达标」**：达标需要产品先定「连续静音多久算断音」的阈值（`docs/22` §11 待决第 ② 条）。
本轮做的是**把量具造成**，让那条阈值一旦定下来就能判。

## 1. 缺口的形状（为什么现有遥测给不出这个数）

`docs/22` §11.5 的原文结论是「**推不出**最长连续静音」，只能给一条下界：

```text
一秒内 k 拍静音、该秒共 B 拍，静音至多被非静音切成 (B − k + 1) 段
⇒ 最长连续静音 ≥ ⌈k ÷ (B − k + 1)⌉ 拍
```

根因有两层：

1. **口径层**：「静音**总占比**」与「**最长连续**静音」是两件事。
   总占比 1% 可以是**一次 600 ms 的断音**（用户听得出「断了」），
   也可以是 **30 个分散的 20 ms 散拍**（用户听不出）—— 累计计数对二者给同一个数字。
2. **实现层**：接收侧 1 Hz 才发布一次快照，而「连续性」是**跨样本**的属性；
   用每秒的计数反推连续性，得到的最多是下界。

本轮的处置正是 §11.5 自己写下的那句：「在引擎播放线程里直接统计最长连续静音拍数，并经**事件**上报」。

## 2. 口径（三个刻意的决定，写进代码注释的同一条理由）

`docs/01-requirements.md` NFR-03 的原文是「2% 丢包下可懂、**无长断音**」—— 量的是**用户听到的东西**。

### 2.1 观察「本路写出去的拍」

播放线程每一拍只有两种命运：写**真实帧**（`DueFrame::Ready`），或补**静音**
（排播等待 / 过期帧丢弃 / 升档 Hold / 欠载）。四种补静音**各有既有计数**（`underruns` /
`late_drops` / `depth_drops`），本模块**不重复记它们**，只回答「这一路连续多久没有真声音」。

因此每拍带一个 `synthetic` 标志，把静音拆成两半：

| 字段 | 含义 | 现有遥测能否看到 |
|---|---|---|
| `synthetic_ms` | **引擎自己补的**静音（欠载 / 等待 / 丢弃 / Hold） | 能（有各自的累计计数） |
| `content_ms` | **有流，但内容是静音**（采集端没人说话、上游静音） | **不能** —— 这正是盲区 |

这张表就是本模块存在的理由：**右列「不能」的那一行**，此前完全不可观测。
（链路一切正常、所有计数器为零，而用户听到的是长时间静音 —— 这不是假设，是「有流没声音」的典型现场。）

### 2.2 漏拍的持续时间**不计入**

播放线程被系统抢占而跨过的拍（`missed`）没有任何「这一拍写了什么」的事实，
它们已由 `record_underruns` 记账。把不确定的东西算进连续性指标会让这个数字失去意义 ——
**宁缺毋滥**：连续性只统计有确凿证据的拍。

### 2.3 只在**段结束**时发事件，进行中的段走**快照**

事件总线是广播式的、有容量上限。一段持续数分钟的静音若按拍 / 按秒发事件，
会把 UI 真正关心的事件（连接、错误）挤掉。
「现在正在静音」这件事实由 1 Hz 快照的 `current_ms` 回答更自然
（外壳本来就每 500 ms 轮询一次遥测）；事件留给「**一段静音完成了**」这个时间点。

## 3. 实现

| 位置 | 内容 |
|---|---|
| `core/crates/audiolink-engine/src/silence.rs` | `SilenceTracker`（纯逻辑：`observe` / `finish` / `snapshot` / `reset`）+ `frame_peak`，12 条单测 |
| `core/crates/audiolink-engine/src/telemetry.rs` | `SilenceTracker` 挂进 `TelemetryAggregator`；`record_playout_beat` / `finish_silence` / `silence()`；`reset()` 一并清零；2 条单测 |
| `core/crates/audiolink-engine/src/runtime.rs` | `EngineEvent::SilenceDetected { peer, segment }`；`playout_main` 的 **5 处写帧点**（4 处补静音 + 1 处真实帧）+ **关流结算**；`Engine::silence_report(peer)` |
| `desktop/src-tauri/src/engine_bridge.rs` | 事件分支（该 match 是穷尽的，新变体必须显式接住） |

**阈值**（都是构造参数，可覆盖）：

| 常量 | 值 | 依据 |
|---|---|---|
| `SILENCE_PEAK_THRESHOLD` | `1.0e-4`（−80 dBFS） | 「听不见」与「很轻」的公认分界，与 `audiolink_audio::SampleStats` 同量级 |
| `MIN_SILENCE_MS` | `200` ms | 抖动目标深度上限 60 ms、排播等待与 Hold 都在单拍量级 → 低于 200 ms 的静音是正常抖动，报出来只会淹没真信号 |

⚠️ **两者都是工程默认值，不是产品定案**：产品确认前**不写进验收表**（与 `--max-underrun-pct` 的建议值同一条纪律）。

**事件带对端 id**：`EngineEvent::Telemetry` 不带对端 id 是多对端下的已知缺陷（契约 §5 的局限，
另有一条看板条目在跟）。新事件**不重复这个缺陷** —— `SilenceDetected` 带 `peer`。

## 4. 验证（全部在本机，可复现）

| 项 | 结果 |
|---|---|
| `cargo fmt --all` | 干净 |
| `cargo clippy -p audiolink-engine --all-targets --all-features -- -D warnings` | **0 告警** |
| `cargo nextest run -p audiolink-engine --lib` | **178 / 178 通过**（含新增 12 + 2 条） |
| `cargo nextest run -p audiolink-engine --test engine` | **50 / 50 通过**（回环延迟护栏 P50 **24 344 µs** / P95 24 699 µs） |
| `cargo clippy -p audiolink-desktop --all-targets -- -D warnings` | 0 告警 |

新增单测各自守什么（挑关键的五条）：

- `a_short_dip_is_not_a_segment`：单拍 / 100 ms 的静音**不得**报成断音（否则正常抖动会淹没真信号）；
- `content_and_synthetic_silence_are_booked_apart`：两半必须分开给数（2.1 那张表就是它守的契约）；
- `in_progress_silence_is_visible_in_the_snapshot`：**只有段结束才发事件**，所以进行中的静音必须能从快照读到 ——
  否则「用户听出断音、遥测一片正常」这个场景依然存在；
- `non_finite_peaks_are_not_treated_as_silence`：NaN / inf 是数据异常，不能被「静音」这一类**掩盖**；
- `finish_closes_an_open_run_for_the_ledger`：关流那一刻正在静音时不能漏掉最后一段（长跑里最典型的漏报形态）。

## 5. 边界（这份数字**不许**被读成什么）

1. **不是「M2 长断音达标」**：产品阈值未定（待决第 ② 条）。本文只证明「量得出来」，不证明「达标」。
2. **不替代** `underruns` / `plc_count` / `late_drops`：它们各自回答不同问题
   （补了几拍 / 掩盖了几帧 / 丢了几帧），本模块回答的是**连续性**。四者并列读才有意义。
3. **单路口径**：统计的是「**本路送出**的样本」，不是 sink 的实际输出波形。多路混音时
   （M3 多成员 / M4 桌面汇聚）某一路静音而另一路有声，用户仍听得到声音，但本路账上会记一段静音。
   这是刻意的：**「这一路没有真音频」本身就是信号**；要判「整台设备是否出声」需要另一层（混音后）统计。
4. **只覆盖写出去的拍**：被系统抢占跨过的拍（2.2）不计入，欠载计数覆盖那一部分。
