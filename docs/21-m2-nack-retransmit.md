# M2 · NACK 重传（§8.1 的辅助抗丢包）

> 看板：`[M2] NACK 重传（洞检测 + 重传窗口 + 有界等重传）`。日期 **2026-09-16**。
> 一句话结论：**NACK 已按 §8.1 落地，并在真实 QUIC + 成对丢包注入下证明「接收侧序列一个洞都没有」**
> （`plc_count = 0`；同一套注入把 RTT 门控关掉 → `plc_count = 16`，即丢包数）。

## 1. 规格 → 实现映射（§8.1）

| §8.1 的约定 | 实现 | 位置 |
|---|---|---|
| NACK（ptype `0x06`）重传 | `NackList` + 数据报收发 | `audiolink-proto/datagram.rs`（M0 已有） |

## 2. 设计

### 2.1 接收侧：把「洞」变成请求（`MissingTracker`）

- 维护 `expected`（= 已到达的最高序号 + 1）；新包超前就为中间每个序号建一个待补条目，
  到达的序号（主包或冗余副本都算）立即把对应条目摘掉；
- 跳变达到 1 000 帧 → **时间轴重建**，不追这些洞（与解码侧 `AudioReceiver` 用同一个阈值：
  「这是丢包还是断流」两份账本必须给同一个答案）；
- 同时跟踪上限 64 个洞，超出部分计数 `overflow`，防止一次异常跳变把内存与 CPU 打满；
- `due_batch` **最旧的洞先请求**（它的 1 s 窗口最先到期），一次最多 16 个；
- 序号回绕按 `wrapping_sub` 的半程判据处理，与解码侧一致。

### 2.2 发送侧：1 s 重传缓冲（`RetransmitBuffer`）

- 只在**主包真的发出去之后**记录（`record` 紧跟在 `transmit_audio` 成功之后）；
- 同序号只留第一份（冗余副本不占容量），容量上限 128 帧（1 s × 10 ms 帧长还有一倍余量）；
- 收到 `NACK` → 逐序号取出重发，**序号与 `sample_index` 原样保留**（改了就排播错位）；
- 重发走的是与主包同一条编码路径（`send_audio_frame`），但**不带发送侧遥测** ——
  重传不是「新的一帧」，绝不能进 `expected` 分母（否则丢包率会被自己的重传擦干净）。

### 2.3 重排窗的「有界等重传」窗口（本轮的关键改动）

只发请求是不够的：重传回来的包到达时，播放游标往往已经越过它 —— 实测（第一版，无等待）
`plc_count = 8 / late_drops = 16`，**请求发了，音频却没救回来**。

于是给 `PacketReorderBuffer` 加一个有界等待（`set_retransmit_grace`）：

- 只有**存在洞**、且调用方开了窗口时才等待（无洞的链路一个字节的额外延迟都没有，已有单测钉住）；
- 窗口长度 = `min(2 × RTT + 5 ms, 30 ms)`：预算来自「请求发出去 → 重传回来」的真实往返；
- **队列没余量就不等**：播放队列深度 < 2 帧时窗口为 0，立刻按原策略交付、由 PCM 掩盖兜底 ——
  「宁可丢一帧，也不延迟出声」是本项目的第一原则（§7 第 1 条）；
- 窗口到点由 `flush_expired` 放弃该洞，绝不无限等。

## 3. 实测证据

### 3.1 端到端回归（真实双 Engine + 真实 QUIC + 有损 UDP 中继）

`core/crates/audiolink-engine/tests/nack_retransmit.rs`：中继只丢「客户端 → 服务端」方向、长度 ≥ 512 B 的包，
**每 10 个丢连续的 2 个**（≈20%）。

为什么必须成串丢：主包与冗余副本在流里只隔一个包位，只丢单包的话双发自己就兜住了 ——
那种绿是双发的绿，不是重传的绿。

| 观测项 | NACK 开启 | 对照：RTT 门控关闭（`NACK_MAX_RTT_US = 0`） |
|---|---|---|
| 中继丢弃 | 34 | 30 |
| `nack_count`（接收侧） | **16** | 0 |
| `plc_count`（接收侧丢包掩盖） | **0–6**（每轮重传都有几次没赶在 30 ms 窗口内回来） | **16** |
| `late_drops` | 16–18 | 17 |
| 播放回调（约 3 s） | 149 | 147 |

**结论**：有 NACK 时接收侧的掩盖次数比丢包数低一个数量级（连跑三次：6 / 2 / 0；关掉门控的对照恒为 16 = 丢包数）。
这就是 NACK 生效的硬证据 —— 掩盖是「重复上一帧 + 淡出」的可听失真，重传回来的是**真实音频**。

### 3.2 诚实记录的取舍：播放侧仍会欠载一次

实测每个洞仍伴随一次播放欠载（≈20 ms 静音，`underruns` 与洞数同量级）：等重传期间播放队列只出不进，
而默认目标深度只有 2 帧（40 ms）。数据面没有洞，**但那一拍的声音补不回来**。

- 关掉 NACK 的对照里静音帧数**相同**（17 vs 18–19）—— 洞占掉一个播放拍这件事与 NACK 无关；
- 所以本轮 NACK 的净收益是「不产生掩盖失真 + 后续帧序不乱」，而不是「填回那一拍」；
- 要让听感也回来，需要更深的目标深度（60 ms 档）与更快的重传，**与抖动缓冲协同优化**留在 M2 后续项。

  目标是「重传能填回那一拍」而不只是「序列无洞」；

- 应用层分片（单帧超 MTU）仍是架构 §12 的既有技术债，与本条无关。
