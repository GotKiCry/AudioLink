## 行为

- Android 的 AudioTrack 队列目标由满灌改为 1440 采样帧（30 ms @ 48 kHz）。仍保留系统分配的容量和诊断档位。容量不等于实际水位。
- FFI 新增 `PcmFeed.playout_buffer_state`，一次回传平台环、待写块和 AudioTrack 的合计待播量与设备目标。快照由 Kotlin 播放线程提供，Rust 不触碰 AudioTrack。停止或未建立播放器时为 `None`；满灌档的目标为 0。
- 引擎将内核待播队列与平台待播量共同纳入预算：网络目标帧数 × 每帧采样数 + 设备输出目标。总量持续超出预算至少一整帧达 500 ms 才回收，每次最多一帧；任意一拍回落就重新观察。短时成批到包不直接触发回收。
- 平台积压超过设备目标至少一帧时，消费并跳过一帧旧 PCM，本拍不向设备补音，让已有下游音频自然消耗；否则仅在内核确有多余帧时取走最旧帧并正常播放下一帧。取走时同步推进序号游标，避免曾经的准入拒绝造成时间轴缺口。计入本地 `depth_drops`，不冒充网络丢包或迟到。
- 主动回收和降档后，下一帧开头用既有 2.5 ms 边界平滑机制衔接。它能减轻突变，但被跳过的音频内容仍然被舍弃，不承诺完全无感；本轮未实现连续变速或 WSOLA。
- 自适应缓冲仍允许弱网升至六帧（默认 120 ms），稳定窗口从 30 秒改为 5 秒。最高六帧到最低一帧需约 25 秒持续满足低抖动、无欠载条件；有新的欠载或无抖动样本会取消降档窗口。
- 全链积压回收限于有实际平台反馈的单源、非预约播放。多源共享输出和 epoch 预约播放不参与，避免一条流改变其他流的时间轴。设备水位未知及满灌对照档停用该控制。

## 起播和旧系统兼容

AudioTrack 的启动门槛默认可能等于容量。只把写入水位限制到 30 ms，可能永远达不到该门槛，尤其在未提供门槛设置 API 的旧设备上。

Android 12 / API 31 以上使用 `setStartThresholdInFrames` 请求一个写块的启动门槛；所有版本仍按实际门槛处理初次填充。已播放后若消费位置连续 100 ms 不前进，允许再次填到启动门槛；恢复消费后继续使用小水位。判定允许写入最后不足一块的尾部，避免 3844 帧门槛卡在 3840。参见 [Android AudioTrack 文档](https://developer.android.com/reference/android/media/AudioTrack#setStartThresholdInFrames(int))。

## 兼容性和指标

本次新增本地 UniFFI 回调方法及记录，Kotlin 绑定与双 ABI 动态库需要一起更新。网络协议未变，Windows 与 Android 可以按原方式连接（连上即用，无需配对码）。现有 `buffer_level_us` 保持内核已解码待播队列口径，未悄悄改为全链总量；网络 RTT 仍不代表端到端出声延迟。

总量控制使用快照，不宣称样本级原子观测：平台环和输出快照的读取可能相差一轮 10 ms 搬运。完整帧余量与持续窗口用于过滤瞬时差异。持续积压回收日志为 `playout backlog recovery`，包含动作和平台水位。

## 验证

验证进行中，原始日志统一保存在 `target/evidence/latency-opt-*`。已通过音频、引擎与 FFI 的 282 项单元测试。

新增验证覆盖：总量在上下游间转移仍会触发回收、80 ms 突发到包不被误判、未知反馈或新抖动取消回收窗口、输出暂缓写入而非补静音、主动跳过后的边界平滑，以及旧 Android 的起播和停滞恢复门槛。另有真实 Rust 播放循环 + 模拟 Android 输出链的回归，检查积压下降时输出不断供、无接收序号缺口。

## 实测边界

本机 `adb devices` 当前没有设备，不能声称用户手机上已经降到某个毫秒数。测试中的 Android 输出是模拟设备；实际 Wi-Fi、扬声器或耳机听感、声学 P50/P95、长时间热运行仍须在同一套设备上测量。默认 30 ms 是输出队列目标，不能写成端到端延迟。
