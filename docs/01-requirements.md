# AudioLink 需求规格（v1）

> 状态：**已与用户逐项确认**（6 轮对齐，2026-09-11）
> 上游参考：`C:\_Project\AudioPipe`（HeHang0/AudioShare 1.7.9 的逐字节镜像，Apache-2.0）
> 本文是一切设计与验收的锚点。实现过程中任何需求变更必须先改本文。

---

## 1. 项目定位

**AudioLink** 是一个局域网实时音频分发系统：把任意节点的声音**低延迟、可同步、可多路混合**地推给局域网内任意数量的其他节点。

**与 AudioPipe 的本质区别**：

| 维度 | AudioPipe（现状） | AudioLink（目标） |
|---|---|---|
| 拓扑 | 1 台 Windows → N 台 Android（单向） | **完全网状**：任意节点均可发/可收，含 Android → Android |
| 编码 | 裸 PCM16（1.54 Mbps/设备） | Opus 48k/20ms（默认 ~160 kbps，可切 PCM 无损档） |
| 传输 | 裸 TCP + 短连接控制 | QUIC（多路复用 + 加密 + 抗丢包） |
| 同步 | 事后 seek 拉平（可听瑕疵） | 时钟同步 + 预约播放（组内 ±10 ms） |
| 稳定性 | 无抖动缓冲，忙则丢帧；异常即静音 | 抖动缓冲 + 丢包隐藏 + 断线自愈 + 遥测可观测 |
| 发现 | UDP 广播（Windows 侧实际 100% 失效） | mDNS/DNS-SD + UDP 广播兜底 |
| 安全 | 无鉴权、无加密，同网段可任意推流 | 自签证书 + TOFU 指纹固定 + PIN 配对白名单 |
| 平台 | WPF（.NET） + Java（无维护） | Rust 内核（桌面 + Android 共用） + Tauri 2 + Kotlin/Compose |
| 功能面 | 音频 + 云音乐 + 灯效 + 远程管理页混杂 | **只做音频链路**，其余全部剔除 |

## 2. 目标与非目标

### 2.1 目标（v1 必须达成）

1. Windows ↔ Android 双向、多节点互推音频：端到端 **P50 80–110 ms（Wi-Fi 现实档）/ 40–55 ms（有线·5GHz 理想档）**，P95 ≤ 150 ms。
2. 同一发送端可推给**多台接收端**，并保证这些接收端**组内同步 ±10 ms**。
3. 同一接收端可**同时接收多路**音频并混音播放。
4. 长时间（≥ 8 小时）连续播放不出现断连、爆音、漂移、静音。
5. 全部能力可通过**内置遥测面板**观测与验收。

### 2.2 非目标（v1 明确不做）

| 排除项 | 原因（已与用户确认） |
|---|---|
| 云音乐播放（网易云/QQ/咪咕） | 非官方 API，合规风险 + 维护负担，且非音频链路能力 |
| 斐讯 R1 氛围灯 | 需 root + `setenforce 0` 全局关 SELinux + 私有 JNI，风险远大于收益 |
| USB / adb 通道及 APK 自动安装 | 依赖高危权限与 adb 分发，改为纯局域网 + 手动安装 |
| 远程 Web 管理页 | 无鉴权 HTTP 面是旧版最大攻击面，直接删除 |
| iOS 接收端 / Web 接收端 | v1 不覆盖（浏览器实时音频缓冲与延迟不可控） |
| 公网穿透 / 跨网络传输 | v1 仅局域网；远程访问交给用户自己的 VPN（Tailscale 等） |
| 文件播放 / 音乐库管理 | 不是播放器，只做声音通道 |

## 3. 使用场景（用户确认，全部支持）

| 编号 | 场景 | 关键要求 |
|---|---|---|
| S1 | 把电脑声音投到旧手机/音箱当无线音箱 | 稳定、长时间、断线自愈。**注意：蓝牙输出（A2DP/SBC/AAC/LDAC）本体延迟 100–300 ms，物理上无法达到 40–110 ms**；达标需内置扬声器 / 有线 / USB DAC / LE Audio（Android 13+，20–30 ms）→ UI 必须在检测到蓝牙输出时明确提示（FR-41） |
| S2 | 游戏 | 延迟优先，USB 已排除 → 依赖 Opus 10/20ms 帧 + 小缓冲 |
| S3 | 看视频 / 追剧 | 音画同步，40–100 ms 内无感 |
| S4 | 音乐欣赏 | 音质优先，可切 PCM 无损档 |
| S5 | 多房间同步播放（同一首歌多设备同时发声） | 组内 ±10 ms |
| S6 | 直播 / 录屏监听 | 长时稳定、低延迟 |
| S7 | 手机内录投给电脑/其他设备（Android 10+） | AudioPlaybackCapture + Opus 编码 |
| S8 | 手机麦克风当无线麦克风 | 需按需启用麦克风采集（**降级路径**，见 FR-07） |

## 4. 功能需求

> 编号规则：`FR-xx` 与路线图（`05-roadmap.md`）和验收清单一一对应。

### 4.1 采集与编码

| 编号 | 需求 | 验收方式 |
|---|---|---|
| **FR-01** | Windows 端采集**指定渲染端点**的系统回环音频（WASAPI loopback），支持运行时切换设备与刷新设备列表 | 界面切换设备后 1 s 内新设备声音出现在接收端 |
| **FR-02** | 采集端支持**采样率档位**（48 kHz 默认 / 44.1 kHz / 96 kHz / 192 kHz）与**位深**（16/24/32 f32 采集，内部统一 48 kHz f32） | 遥测面板显示实际采集格式 |
| **FR-03** | **声道路由**：立体声 / 仅左声道 / 仅右声道 / 左→A 设备 + 右→B 设备（双路监听） | 左右分流测试音频验证 |
| **FR-04** | 编码：**Opus 48 kHz 立体声、20 ms 帧、默认 160 kbps**，支持 10 ms 帧档；弱网自动降码率（160→128→96 kbps） | 遥测显示实时码率随丢包/延迟变化 |
| **FR-05** | **PCM 无损档**：可选禁用压缩（PCM16 LE 裸流），用于千兆/本机回环场景 | 遥测显示 codec=pcm |
| **FR-06** | Android 端**系统内录**（`AudioPlaybackCapture`，Android 10+ / API 29+）作为发送源；< API 29 时该入口置灰并给出原因 | 真机验证：API 29+ 可发送；API 24–28 显示"不支持本机内录" |
| **FR-07** | Android 端**麦克风采集**作为可选发送源（降级路径，需运行时 `RECORD_AUDIO` 授权） | 真机录音测试 |
| **FR-08** | Windows 端也能接收其他节点音频并通过**指定渲染端点**播放 | PC 播放手机推来的音频 |

### 4.2 传输与组网（完全网状）

| 编号 | 需求 | 验收方式 |
|---|---|---|
| **FR-09** | 每个节点同时具备**监听与发起**能力（对等节点模型，无固定 server/client） | 任意两节点互推 |
| **FR-10** | 传输层使用 **QUIC**（桌面 `quinn`，Android 复用 Rust 内核），音频走**不可靠/半可靠数据报**，控制走**可靠流** | 抓包/遥测显示双通道 |
| **FR-11** | 单连接支持**多路音频流复用**（如立体声 + 麦克风同时） | 遥测显示 stream 数 |
| **FR-12** | 接收端**多路混音**：同时接收 ≥ 4 路音频并混音输出，每路可独立调音量/静音 | 4 路并发测试 |
| **FR-13** | 发送端容量：单发送端同时推给 **≥ 8 台**接收端 | 8 设备压测（可用多台模拟器/真机） |
| **FR-14** | 音频流**优先级与拥塞控制**：音频不可靠通道带自适应重传（FEC + NACK），控制通道独立不相干阻塞 | 弱网（限速/丢包注入）测试 |

### 4.3 发现与配对

| 编号 | 需求 | 验收方式 |
|---|---|---|
| **FR-15** | **mDNS/DNS-SD 服务发现**（服务类型 `_audiolink._udp`），列出在线节点、名称、能力（可发/可收/内录支持）、版本 | 界面 5 s 内列出同网段全部节点 |
| **FR-16** | **UDP 广播兜底发现**（mDNS 被 AP 隔离/组播屏蔽时），端口可配置 | 关闭 mDNS 后仍能发现 |
| **FR-17** | **PIN 配对**：首次连接由接收端显示 6 位数字码，双方确认后写入**信任设备白名单**（TOFU，指纹固定） | 未配对设备连接被拒绝并提示配对 |
| **FR-18** | 白名单**可查看/移除**；支持"临时允许一次"（访客模式） | 界面可撤销信任，撤销后连接立即失效 |
| **FR-19** | **自签证书**持久化（首次生成后复用），节点身份 = 证书指纹（SHA-256，界面显示短码） | 重启后仍是同一身份 |

### 4.4 同步（多房间）

| 编号 | 需求 | 验收方式 |
|---|---|---|
| **FR-20** | **时钟同步**：NTP-like 多次采样（≥ 8 次）+ 最小 RTT 过滤 + 单调时钟校正，节点间时钟偏差 **< 2 ms** | 遥测显示 clock offset 与收敛曲线 |
| **FR-21** | **预约播放**：发送端给出播放时间戳，接收端按本地校正后的时钟在指定时刻出声（不是事后 seek） | 遥测显示 schedule lead/lag |
| **FR-22** | **临时同步组**：发送端勾选 N 台接收端组成组，组内所有接收端**同时出声，偏差 ≤ ±10 ms（P95）** | 双机录音分析法（敲击测试 + 波形对齐） |
| **FR-23** | 组成员动态加入/退出不影响在场成员播放（无需重连） | 运行中加入第 3 台设备验证 |

### 4.5 控制面

| 编号 | 需求 | 验收方式 |
|---|---|---|
| **FR-24** | **远端音量控制**：发送端可调接收端播放音量（映射到接收端媒体音量或数字增益），接收端可锁定上限 | 双端同时观察音量变化 |
| **FR-25** | **系统音量联动**：Windows 端跟随系统音量变化的开关（旧版已用此能力） | 拖动系统音量，接收端跟随 |
| **FR-26** | **一键连接/断开**、连接状态实时回显（未连接/握手中/推流中/重连中） | UI 状态机与遥测一致 |
| **FR-27** | **断线自愈**：网络中断恢复后 ≤ 3 s 自动重连并恢复播放；重连期间 UI 明示 | 拔网线/关 Wi-Fi 测试 |
| **FR-28** | **静音/欠载自愈**：接收端检测到 ≥ 2 s 无输出但链路正常时自动重建播放器（旧版"永久静音"缺陷的根治） | 注入异常后验证恢复 |

### 4.6 桌面端（Tauri 2 + React）

| 编号 | 需求 |
|---|---|
| **FR-29** | 主界面：**卡片式节点列表 + 状态仪表**（在线状态、连接状态、实时延迟/码率/丢包、音量滑块） |
| **FR-30** | **托盘常驻**：托盘菜单可快速连接/断开/静音、显示当前推流节点数；关闭窗口 = 最小化到托盘 |
| **FR-31** | **开机自启**（可关）与**启动后自动连接上次设备**（可关） |
| **FR-32** | **遥测面板**：每会话 RTT、抖动、丢包率、码率、缓冲深度、估算端到端延迟；曲线与 P50/P95 统计；**日志导出**（zip，含脱敏） |
| **FR-33** | **中英双语**、深浅色主题、窗口尺寸与位置记忆 |
| **FR-34** | **自动更新**：检查 GitHub Releases，签名校验后提示安装 |

### 4.7 Android 端（Kotlin + Compose）

| 编号 | 需求 |
|---|---|
| **FR-35** | 单页信息架构：顶部**本机状态卡片**（接收中/发送中、延迟、码率、音量），下方**节点列表**（点击连接/推流/配对），底部导航进设置 |

## 5. 非功能需求（NFR）

### 5.1 延迟预算（端到端，48 kHz / 20 ms 帧 / Wi-Fi 5 以上）

| 环节 | 预算 | 备注 |
|---|---|---|
| 采集缓冲（WASAPI） | 10–20 ms | 事件驱动，不用 100 ms 默认引擎缓冲 |
| Opus 编码（20 ms 帧） | 20–22 ms | 单帧必须凑满才能编码 |
| 网络排队 + 传输 | 2–10 ms | 局域网，QUIC 数据报 |
| 抖动缓冲 | 20–40 ms | 自适应（默认 2 帧） |
| 解码 + 播放提交 | 10–20 ms | AudioTrack 低延迟模式（API 26+） |
| **档位 B（Wi-Fi 现实）P50** | **80–110 ms** | **默认验收档** |
| **档位 A（有线 / 5GHz 理想）P50** | **40–55 ms** | 需 10 ms 帧 + 最小抖动缓冲，**非承诺值** |

> **不得对外承诺单一数字**：Wi-Fi 下延迟分布长尾明显（上游 issue #7 实测「哪怕最低码率也会一顿一顿」，社区结论是「只能换有线」）→ 验收按 **P95/P99** 设计，不看均值。
> **同步与延迟是两个独立指标**：Snapcast 端到端默认 1000 ms 而设备间偏差 < 0.2 ms。本项目的 40–110 ms 指**端到端**，±10 ms 指**设备间同步**，两者分别验收。

### 5.2 其它指标

| 编号 | 指标 | 目标 |
|---|---|---|
| NFR-01 | 组内同步偏差 | ≤ ±10 ms（P95） |
| NFR-02 | 抗抖动 | 网络抖动 ≤ 30 ms 无爆音 |
| NFR-03 | 抗随机丢包 | 2% 丢包下可懂、无长断音 |
| NFR-04 | 首帧时间 | 连接建立到出声 ≤ 300 ms |
| NFR-05 | 长时稳定性 | 8 h 连续播放：0 崩溃、0 静音、0 累积漂移 |
| NFR-06 | 默认码率/带宽 | 160 kbps/流（PCM 无损档 1.536 Mbps/流） |
| NFR-07 | CPU 占用 | 桌面端采集+编码 < 5% 单核；Android 解码+播放 < 5% |
| NFR-08 | 内存 | 桌面常驻 < 150 MB；Android 常驻 < 80 MB |
| NFR-09 | 冷启动 | 桌面端 < 1.5 s 可交互；Android 冷启 < 1.2 s |
| NFR-10 | 兼容性 | Windows 10 1809+ / Windows 11；**Android 8.0+（API 26+）** —— API 26 是 `AudioTrack.PERFORMANCE_MODE_LOW_LATENCY` 的门槛，低延迟能力与最低版本绑定 |
| NFR-13 | **零重采样链路**（硬性） | 采集 / 内核内部 / Opus / 播放**全程锁 48 kHz**；Android 侧**禁止**出现任何额外采样率转换（Oboe 实测：多做一次 SRC 输出延迟 +~160 ms） |
| NFR-14 | **低延迟模式必须显式开启**（硬性） | Android `AudioTrack` 必须使用 `PERFORMANCE_MODE_LOW_LATENCY` + `WRITE_NON_BLOCKING`（官方实测：漏设为 ~205 ms，正确设置 ~20 ms 量级） |
| NFR-11 | 安全 | 全链路加密（QUIC TLS1.3）；配对前不可传输音频；无开放代理/无未鉴权 HTTP 面 |
| NFR-12 | 可观测 | 每会话真实指标可导出；崩溃有本地日志（脱敏，不含音频内容） |

### 5.3 平台与版本约束（调研实测结论，**必须遵守**）

| 约束 | 说明 |
|---|---|
| Android `compileSdk = 37` / `targetSdk = 36` | Compose 1.12+ 必须 compileSdk 37；但 **targetSdk 37 会强制 `ACCESS_LOCAL_NETWORK` 运行时权限**，导致局域网收发在未授权时 EPERM → v1 锁 targetSdk 36，权限门禁记入技术债 |
| Android 后台音频 | targetSdk ≥ 37 时后台播放要求 FGS 具备 while-in-use 能力，否则音频写入被**静默吞掉** → 同样规避，但需在 FGS 声明中预先合规 |
| JDK | 构建必须 JDK 17（本机 `JAVA_HOME` 当前指向 Java 11，Gradle 9 会直接拒绝启动） |
| 低延迟播放 | `AudioTrack.PERFORMANCE_MODE_LOW_LATENCY` 需 **API 26**；API 24/25 走普通模式（延迟更高，验收时单独标注） |
| 桌面端 | Tauri 2 依赖 WebView2（Win10 1809+ 通常自带，缺失时引导安装） |

## 6. 验收标准（v1 完成的定义）

1. **单链路**：PC → 单台 Android，遥测 **P50 ≤ 110 ms、P95 ≤ 150 ms**，P99 无持续尖峰；8 h 无故障（S1/S3/S6）。
2. **多接收端**：PC → 3 台 Android 并发，各自独立音量，无相互干扰。
3. **同步组**：PC → 2 台 Android 组内 ±10 ms（双机录音对齐验证）。
4. **多路混音**：2 部手机同时推给 PC + PC 同时推给手机，PC 侧混音输出无爆音。
5. **双向网状**：Android(内录) → PC 与 Android(内录) → Android 互通。
6. **弱网**：限制 5 Mbps + 2% 丢包 + 30 ms 抖动，仍可听、无长断音、码率自适应生效。
7. **配对安全**：未配对设备连接被拒；移除信任后立即失效。
8. **自愈**：拔网 10 s 后恢复 ≤ 3 s 自动续播；注入播放器异常后自动重建。
9. **排除项确认**：仓库中不存在云音乐、灯效、远程 Web 页、adb/USB 相关代码与依赖。
10. **零重采样 + 低延迟模式**：Android 端全链路 48 kHz（无任何 SRC）且 `PERFORMANCE_MODE_LOW_LATENCY` 实际生效（NFR-13/14）。
11. **蓝牙提示**：输出为蓝牙时 UI 给出延迟劣化提示（FR-41）。

## 7. 需求追溯表（用户决策 → 需求）
