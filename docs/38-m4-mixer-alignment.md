**掉队帧（partial_frames）就是「对齐好不好」最直接的读数**：两路都持续供帧时它应当长期为 0；
某一路开始掉队，它会立刻涨起来 —— 这比"听起来有没有问题"可靠得多。

那条实测数据（298 帧里只有 1 帧是单路）说明：稳态下两路都在稳定供帧，混音**不是靠补静音撑场面**。

## 2. 诚实的缺口：多源之间没有共同时间基准

协议 §7 的 epoch 是「**发送端**指定、接收端排播」。而 M4 的拓扑（2 部手机 → 1 台 PC）里，
两个发送端是两个独立的源，它们各自的采集时间轴不同 —— 当前实现里：

| 能力 | 现状 |
|---|---|
| 每条接收会话各自按 epoch 排播 | ✅ 已实现（docs/28、docs/29） |
| 同一发送端 → 多台接收端对齐 | ✅ 已实现（同一 epoch 广播给成员） |
| **多个发送端之间**采样级对齐 | ❌ **未实现** —— 缺少一个平级的基准来源 |

要做到第三点，需要两件新东西：

1. **接收端（PC）作为基准来源**：由它广播 epoch 给所有发送端，而不是只能由发送端指定；
2. **发送端的「预约发送」**：发送端把 epoch 用在自己的**发送时间轴**上（sample_index 的 0 点
   对齐到 epoch），而不是从自己启流的瞬间开始计数。

这两件都不在本轮范围内，已经作为独立待办立项（见面板），而不是塞进文档角落。

**2026-09-17 第 63 轮复核：两件其实都已经实现了，缺的是「接线到测试」与「可观测出口」。**
`Engine::broadcast_epoch(lead_ms)`（`0x44`）把接收端的共同原点广播给所有已连接对端；发送端在
`ControlRequest::ReceiverEpoch` 分支里 `hub.apply_epoch(...)` 落到采集枢纽的原子量上，采集线程每帧前
读它并据此对齐编号。本轮补上的是证据（§5），并顺手补了那个缺失的观测出口。

## 5. 共同基准的回环验证（2026-09-17 第 63 轮补）

### 5.1 先补一个可观测出口

对齐与否原本**没有任何当场可读的量**：`CaptureHub.epoch_us` 是个 `AtomicI64`，从建到现在没有出口，
验收只能事后在混音音频里听出「两路错开几十毫秒」。本轮加了：

```rust
Engine::capture_epoch_us() -> Option<i64>   // None = 没有采集枢纽；i64::MIN = 有枢纽但还没收到广播
```

### 5.2 端到端测试

新增 `tests/engine/mixer_epoch.rs`：1 台 PC（接收端 + 混音方）+ 2 台手机（发送端），真 QUIC + 真 PIN。

```text
[mixer-epoch] 广播前 A=Some(-9223372036854775808) · B=Some(-9223372036854775808)；广播后 A=107377 · B=107377
```

- 广播**前**：两端都是 `i64::MIN`（未对齐）—— 这是对照组，证明这个量的确有区分力；
- 广播**后**：两端拿到**完全相同**的值（连跑 4 次，每轮都是 A == B）—— 这正是「共同时间基准」的定义。

断言还包括 `broadcast_epoch` 的返回值为 2（两条会话都收到了广播）。引擎集成 30 项 + 单测 150 项全绿。

### 5.3 仍未做（诚实口径）

- **真机**：两台手机 → 一台 PC 的实际混音听感与输出延迟差异，仍属 M4 的真机验收；
- 掉队自动处理（只统计与上报，不自动重排某一路）不变；
- 采样级对齐的**精度**：本轮的证据是「两端拿到同一个原点」，**不是**「混音结果已经对齐到 X ms」——
  那个数字要在真机上量（共同基准是必要前提，不是充分条件）。
