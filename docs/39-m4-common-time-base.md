# M4 · 多源共同时间基准（接收端广播 epoch）

> 日期 **2026-09-16**。一句话：上一轮把 M4 混音对齐的**缺口**写清楚了（两个发送端之间没有共同时间基准），
> 这一轮把缺口补上 —— 协议方向反过来：**接收端作为基准来源广播 epoch（`0x44`）**，各发送端据此把自己的
> 样本编号对齐到同一条时间轴上。

---

## 1. 为什么 `GROUP_EPOCH`（`0x43`）不够

§7 的 epoch 是「**发送端**指定、接收端据此排播」：一台发送端 → 多台接收端，大家在同一个组时刻起播 ✓。

但 M4 的拓扑是「**2 部手机 → 1 台 PC 混音**」：两个发送端彼此独立，`sample_index` 的原点分别是
各自启流的瞬间（相隔几十毫秒到几秒不等）。接收端按编号取样本混音时，两路取到的**不是同一时刻的声音** ——
音频会像回声一样错开。

缺的是一个**平级的基准来源**：混音方（接收端）才是最清楚「共同原点该在哪」的那一端。

## 2. 设计：把方向反过来

| 方向 | 帧 | 语义 |
|---|---|---|
| 发送端 → 接收端 | `GROUP_EPOCH`（`0x43`） | 发送端指定基准，接收端据此**排播**（同一发送端 → 多台接收端对齐） |
| **接收端 → 发送端** | **`RECEIVER_EPOCH`（`0x44`）** | **接收端广播基准，发送端据此对齐自己的发送时间轴**（多台发送端 → 一台接收端混音对齐） |

同一个载荷（`epoch_id, epoch_local_us, lead_ms`）两个方向，各自换算：

- `epoch_local_us` 由广播方取**本机**单调时刻 + `lead_ms` 提前量；
- 接收端用它自己的 §6 时钟偏移换算到本端轴：`本端时刻 = 对端时刻 − offset_us`
  （`offset_us` = 对端时钟 − 本端时钟，见 `audiolink-net::clock`）。

### 2.1 发送端怎么"对齐"

采集线程持有 `HubClock`（编号分配器）。收到共同基准后 `align_epoch(start_at_us)`：

```text
未对齐：sample_index 的原点 = 本机启流瞬间   → 两路编号不可比
对齐后：sample_index = 0 落在同一个绝对时刻 → 同一编号 = 同一时刻的声音
```

一个刻意的细节：**到点之前一帧都不发**（`HubClock::next` 返回 `None`，采集循环丢掉这段）。
若把这些帧也发出去，它们的编号在接收端属于「epoch 之前的时间」，会和另一路同样错位的帧混在一起 ——
那正是要修掉的东西。`seq` 不受对齐影响：它只管丢包检测，不承担时间轴语义。

实现要点：`CaptureHub` 上用 `AtomicI64` 传递基准（`i64::MIN` = 未收到），采集线程每帧前读一次 ——
实时路径**不加锁、不分配**，与会话线程解耦。

## 3. 实测（真实双 Engine + 真实 QUIC 回环）

`core/crates/audiolink-engine/tests/receiver_epoch.rs`：两台发送端 → 一台接收端，配对 + 开流后由接收端广播基准。

```text
M4 共同基准：广播 2 条会话 · 对齐前 148 帧（掉队 1）· 对齐后 298 帧（掉队 1）
```

| 断言 | 结果 |
|---|---|
| 广播覆盖到全部已连接会话 | **2 / 2** |
| 对齐后两路仍各占一路 | ✅ |
| 对齐不打断供帧 | 148 → 298 帧（+150，3 s） |
| 对齐后掉队帧比例 | 1 / 298 = 0.3% |

单测（`runtime/playout_tests.rs`，HubClock 的既有测试家）：到点前不发帧、到点后编号从 0 起算、
重新对齐不动 `seq`、序号回绕语义不变 —— 共 3 项。

上面测到的是「广播到达 + 对齐不打断供帧」。**真正的验收判据**（两路同一编号对应同一时刻，误差 < 1 帧）
~~现在读不到：接收端没有暴露「每路流的 `sample_index` ↔ 到达时刻」。~~
→ **口径更新（§6 第二轮已补上，2026-09-16）**：读得到了 —— `Engine::stream_axes()`（`runtime.rs:1221`）
暴露每路 `StreamAxis { peer, sample_index, at_ms }`，接收轴 `rx_axis` 见 `runtime.rs:505,550`。同一次「现在」
推算的两路跨度实测 **144 样本 = 3 ms**，优于 1 帧（960 样本）的判据。仍未做的只剩 §6.2 两条：桌面 UI 展示、真机多机验收。

## 6. 补上观测入口：`Engine::stream_axes()`（2026-09-16 第二轮）

§4 说的「缺一个直接读数」这一轮补上了：

- 接收端每收到一个音频数据报，就把「最近一帧的 `sample_index` ↔ 到达时刻」打包成**一次** 64 位原子写
  （高 32 位毫秒、低 32 位编号）—— 读者不会读到「新编号 + 旧时刻」的撕裂组合；实时路径不加锁、不分配。
- `Engine::stream_axes()` 暴露每路的 `StreamAxis { peer, sample_index, at_ms }`，
  `StreamAxis::index_at(now_ms)` 用**同一个**「现在」推算该路当前的编号。
- 判据：用同一个 `now` 推算两路编号，**跨度**就是时间轴错位量。

### 6.1 它当场抓出一个真缺陷

补上观测之后，第一条断言就红了：对齐前跨度 **72096** 样本（1.5 s，符合刻意制造的错位），
**对齐后仍是 72192** —— 对齐根本没生效。

根因：上一轮只把 `0x44` 加进了 `OpCode` 枚举，**忘了加进 `OpCode::ALL` 与 `OpCode::from_u8`**，
于是 `dispatch` 把它当未知命令码忽略（`IgnoredUnknownOp`），发送端从未收到共同基准。

这正是上一轮那个绿灯测试测不出来的东西：它只验证了 `broadcast_epoch` 返回 2（帧确实发出去了），
没有验证对端**处理**了它。**没有直接读数，就没有验收**。

修好之后（`ALL` 24 → 25 项、`from_u8` 补 `0x44`）：

| 读数 | 值 |
|---|---|
| 对齐前两路编号跨度 | **72048 样本**（≈1.5 s 错位） |
| 对齐后两路编号跨度 | **144 样本**（= 3 ms；1 帧 = 960 样本） |

顺带被三处**既有护栏**当场拦住（这正是它们存在的意义，全部就手修掉）：
`OpCode::ALL` 数量断言（proto 往返回归）、`控制帧24个opcode全扫往返一致`（net）、
`m1_samples_cover_every_implemented_opcode`（engine dispatch 样本表）。
