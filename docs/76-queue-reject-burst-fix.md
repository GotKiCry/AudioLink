# 批式到达下的满队列拒收治理（队列容量 + 占位帧让位）

日期：2026-10-13。范围：接收侧 Rust 待播队列（普通单流播放）；续接 `docs/73`（三写入源）、
`docs/74`（A/B/C 分量）、`docs/75`（拒收后游标恢复）。

## 背景

PJZ110 现场（PC → Android，10 ms 低延迟档，Wi-Fi）：1767 s 窗口内节拍超时 A=15、
**满队列拒收 B=314**、游标追赶 C=110，而供给欠载仅 21 —— B 线是绝对主嫌（`docs/75`
实测也看到 B 随电脑负载增长）。`docs/75` 修好了「拒收之后怎么恢复」（游标跳队头），
但拒收本身为什么持续发生没有回答。

## 复现装置与根因

新增 `tests/engine/queue_reject_burst.rs`：双端 10 ms 帧 + NullPlayout，中间架一个
`BatchRelay`，按 Wi-Fi 节电/聚合的真实形态把 ≥512 B 的音频大包按 100 ms 批窗攒批放行
（小包透传），每 40 批整批丢一次，跑 30 s 采样增量计数。

**修复前实测：水位 P50 80 ms、峰值 150 ms 顶格，underruns +233，A 0 / B 297 / C 167。**

根因链（每一环都被复现数字钉住）：

1. Wi-Fi 批式到达 → 到达间隔抖动 p95 顶高 → `AdaptiveJitterDepth` 升档到 120 ms 上限
   （10 ms 档 = 12 帧）；
2. 旧待播队列容量是固定 `PLAYBACK_QUEUE_FRAMES = 16`（10 ms 档仅 160 ms）：深度占掉 12 帧后
   只剩 4 帧余量，一个 ~100 ms 批次（~10 帧）一次性投递即溢出 → B；
3. 接收侧对一个序号洞会**连发 N 帧掩盖占位帧、最后才是真实帧**：整批丢失后的下一批到达时，
   占位帧先把队列顶满，真实帧反而被拒（优先级倒置）；
4. B 拒收留下永久序号缺口 → 播放端 C 追赶记欠载 → 欠载阻止深度降档
   （`observe()` 里 `underruns > 0` 时 `wanted.max(target)`）→ 深度钉死上限 → 自锁环。

## 做法与取舍

两处改动，都在接收侧会话任务 → 待播队列这一条投递路径上：

- **帧长感知容量**（`runtime/jitter.rs` `playback_queue_frames`）：容量从固定 16 帧改为
  墙钟口径「上限目标 120 ms + 重排容量 60 ms + 批次余量 120 ms = 300 ms」按帧长换算，
  下限 16 帧。10 ms 档 = 30 帧；20/40/60 ms 档夹到下限 16，**历史行为不变**。
  容量只是余量不是延迟：稳态水位仍由自适应目标深度（≤120 ms）决定。
- **占位帧让位**（`runtime.rs` `push_playback_frame` / `PlayoutHandle::should_yield_conceal`）：
  掩盖占位帧有两条让位线，先到先让 —— ① 水位达到投递上限
  `conceal_ceiling_frames = 当前目标深度 + 一个重排窗`（10 ms 档 8~18 帧，随自适应深度联动）；
  ② 队列只剩最后一格（兜底）。让位 = 不进队、不算拒收（不进 `queue_rejects`）、缺口经
  `note_dropped_seq` 标记给播放端，游标到点走 `docs/75` 的跳队头恢复。
  占位帧的职责只是防止播放端走到洞时欠载；水位已够时它是纯压载。真实帧不受让位线约束，
  只有队列真满才被拒（那才是该计数的 B）。

取舍说明：

- 让位的占位帧不单独计数是刻意的：掩盖生成量已在 `plc_count`、洞在 `lost`，证据链不缺；
  进程内 `UnderrunBreakdown` 不加字段，冻结的 `StreamStats` wire schema 不动。
- 低水位下单包/双包洞的掩盖行为**不变**（上限 = 目标 + 6 帧，远高于低档位水位），
  只有水位已经够深时才跳过合成音频直接跳队头 —— 与「宁可丢一帧，也不延迟出声」同口径。
- 没走 `docs/12` §11.12–14 被真机否决的两条老路（水位层每拍丢帧 / 准入拒绝）：
  本修复不动结算纪律（仍 1 帧 / 500 ms、保留目标之上一整帧摆幅），只改「谁有资格进队」。

## 验证

复现装置同一装置、修复后：

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| 水位 P50 / 峰值 | 80 ms / 150 ms（顶格） | 110 ms / 240 ms |
| underruns 增量 | 233 | 17 |
| late_drops 增量 | 530 | 208 |
| A 节拍超时 | 0 | 0 |
| **B 满队列拒收** | **297** | **0** |
| **C 游标追赶** | **167** | **0** |

（修复中途还有一版只让最后一格：B 297→2，证明占位帧顶满队列是残留 B 的来源，
于是让位线上移到「目标 + 重排窗」。）

- 断言已写成回归形态：批式到达下 `queue_rejects == 0`、节拍超时 ≤ 2。
- **门禁并发下的 flaky 治理**：该用例是 30 s 真实 QUIC + 实时播放的实验。全量套件并发时
  宿主 CPU 饥荒会把会话任务拖出实时性 —— 插座攒出 >容量 的超大批次，容量作为背压拒收
  （B 42 与 B 2 各出现一次，`underruns` 同步飙到 56~68，与干净跑的 12~17 明显两个世界）。
  这与被修机制（到达形状驱动）不是同一来源，但断言分辨不了。处置（`.config/nextest.toml`）：
  该用例 `threads-required = "num-cpus"`（实时实验独占整机调度窗口）+ `retries = 1`，
  并让 A/B/C 读数常驻可见（同 `latency_budget` 先例）。
- `audiolink-engine` 库 204/204 通过；新增钉机制用例：
  `conceal_frames_yield_at_the_depth_ceiling`（让位线①）、
  `conceal_frames_yield_the_last_queue_slot_to_real_audio`（让位线②）、
  `conceal_ceiling_is_target_depth_plus_one_reorder_window`、
  `playback_queue_capacity_is_wall_clock_aware_with_a_floor`（容量换算表）。
- 门禁全套：`cargo fmt --all --check`、非桌面 clippy `-D warnings`、非桌面 nextest
  （569 通过，本用例首次 TRY 被宿主饥荒干扰后由重试转绿）、桌面 clippy、
  `cargo test -p audiolink-desktop`（42 通过）、`desktop/pnpm build` 全部通过。

## 未验

- 复现装置的批窗（100 ms）与整批丢失节奏（1/40）是参数化的近似，不是 PJZ110 所在
  Wi-Fi 的实测分布；真机 B 线是否归零需要装回手机用区间增量复核（累计值不清零）。
- 极端情形（>300 ms 的 Wi-Fi 停摆后一次性补投）超出新容量时仍会拒收 —— 那是设计内的
  最后防线（停摆期间队列已被播放掏空，拒收按缺口跳队头恢复），但未经真机验证。
- 未做声学连续性录音与长时间 soak；A 线（Android 播放线程调度）不是本次治理对象。

## 2026-10-13 补充：真机复测暴露单槽标记病灶 → 多槽标记集 `RejectedMarks`

**真机数据（PJZ110，装第一版修复后，区间时长 1324 s）**：A=8、**B=1065**、**C=459**、
供给欠载 30、系统欠载 0、播放环读空 30、环溢出丢弃 +28320 样本（≈590 ms，量小）、
静音填充 14400 样本。输出流连续（已写入 63508320 样本 ≈ 1323 s ≈ 区间时长），
但用户听感「时不时卡顿、缓冲水位跟着爬升」。对照旧构建基线（1767 s：B=314、C=110），
B/C 不降反升 —— 第一版修复把「占位帧顶满队列」治好了，却把另一个病灶暴露出来。

**根因**：`docs/75` 的拒收缺口标记是**单槽位** `AtomicU64`（CAS 只在槽为 0 时写入）。
播放游标比接收前沿落后一个水位深度（最多 30 个序号），这段窗口内的第二个缺口标记
被丢弃；该缺口在播放端只能走「未标记」贵路径 —— 逐拍追赶（C+1/拍）+ 深度 +1 粘性
升档 + Hold 补水拍（不消费队列）→ 卡顿 + 水位阶梯爬升 + 占用膨胀 → 真实帧撞满
30 帧队列被拒（B）。C=459 直接证明未标记缺口在密集发生；占位帧让位与满队列拒收
在弱网波动期成簇出现，单槽装不下。

**修法**：单槽 → **16 槽原子标记集 `RejectedMarks`**（`runtime.rs`，写侧会话任务单生产者、
读侧播放线程单消费者，全原子免锁）。`mark()` 优先占空槽，槽满轮转覆盖最旧 —— 被覆盖的
洞退回贵路径，与单槽时代最坏行为相同，不会更糟。`covers_gap(expected, distance)` 顺手
清理命中槽与游标身后的陈旧标记。16 槽依据：在窗缺口 ≤「队列容量 30 + 重排在飞 ~18」
个序号，正常丢包形态两倍余量。不回调让位阈值 —— C=459 证明贵路径才是病灶。

**验证**：`audiolink-engine` 库 204/204 通过；复现装置（同一 `queue_reject_burst.rs`，
单跑）A=0 / **B=0** / **C=0**，underruns 14。钉机制测试更新：
`full_queue_rejection_marks_every_gap_and_recovers_at_each_accepted_frame`
（多槽语义：窗口内每个缺口都留标记、跳过的标记清除、前方标记保留、未标记缺帧仍逐拍
掩盖）、`rejected_gap_recovery_preserves_wrapping_sequence_order`（回绕）、
两个让位测试改断言 `is_marked`。门禁全套（fmt / 非桌面 clippy / 非桌面 nextest /
桌面 clippy / 桌面 test / `pnpm build`）通过。

**未验**：真机复测待用户 —— 区间清零后预期 C≈0、B 大幅下降、水位不再阶梯爬升。
若 B 仍高，下一嫌疑是手机端会话任务被 GC/调度饥荒（UniFFI `List<Float>` 每帧
~1920 个装箱对象）攒出超大批次 —— 届时在真机路径上加证据，不再用复现装置猜。
