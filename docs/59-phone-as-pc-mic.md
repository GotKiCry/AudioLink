# 手机当电脑麦克风（虚拟录音设备）—— TODO 与技术路径

> 状态：**TODO**（2026-09-18 用户指定："这个功能先改为 TODO，后面再做"）
> 触发：真机联调时用户指出 —— 现在的形态是"手机麦克风 → 电脑播放器出声"，
> 而期望的形态是"**把手机麦克风当成电脑的麦克风**"。

## 1. 两条路的差别（先钉住口径，避免再次跑偏）

| | 当前实现（M4 既有链路） | 用户期望的形态 |
|---|---|---|
| 数据流 | 手机麦克风 → Opus → QUIC → PC 解码 → **WASAPI RenderSink（默认扬声器）** | 手机麦克风 → …… → PC 上**作为录音设备**被别的程序选为输入 |
| 典型场景 | 手机当"无线话筒"，声音从 PC 扬声器/耳机放出来 | 手机当"PC 的麦克风"：微信语音、会议、直播等**需要麦克风输入**的程序直接用 |
| **终点类型** | **渲染端点（output）** | **捕获端点（input）** |

⇒ 两者**前半段完全相同**（采集 → 编码 → 传输 → 解码），差别只在"把解出来的 PCM 送到哪里"。

## 2. Windows 侧的硬约束（它决定可行路径）

**普通应用无法"注册一个麦克风设备"** —— 录音设备由**内核态音频驱动**提供。
因此只有三条路：

| 路径 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A. 借现成的虚拟声卡**（推荐） | 用户安装 VB-CABLE / Virtual Audio Cable 之类；我们把音频**渲染到它的输入端**，其他程序把它的**输出端**选作麦克风 | 需要用户装第三方虚拟声卡；我们**零驱动开发** | ✅ 首选 |
| B. 自研虚拟音频驱动 | WDM + APO + EV 代码签名 | 极高（驱动开发 + 签名链 + 兼容性矩阵） | ❌ 不做 |
| C. 依赖 Windows 内建"立体声混音" | 让用户在其他程序里选它 | 新机器上普遍已被移除 | ❌ 不可依赖 |

## 3. 实现清单（真做的时候照这个走）

1. **桌面端：确认"输出设备"能选到虚拟声卡的输入端** ——
   现成能力：`RenderSink::open(DeviceSelector)` 已支持指定渲染端点，桌面 UI 的端点选择器也已存在；
2. **桌面端：把它做成一个明确的形态**（例如"手机当麦克风"预设）并在 UI 里解释
   **为什么需要先装虚拟声卡**（这不是我们偷懒，是 Windows 的设备模型）；
3. **文档**：把上面第 2 节写进用户手册（否则用户会以为是软件缺陷）；
4. **不需要改**内核 / 协议 / Android 侧 —— 前半段与当前实现一字不差。

## 5. 当前已知的收尾缺口（与本 TODO 无关，但同属这条链路）

手机 → 电脑方向的**开流**仍未成功（手机 UI 显示「已连接 · 发送中」，但桌面端遥测无数据）。
根因已定位（见 `docs/58-android-uplink-fixes.md` §7.5 与看板条目）：
`canStartSend` 不看 `engineCanSend`、引擎重启判定有启动窗口洞、`startSend` 的真实失败被
`AlreadySending` 文案盖住。**注意**：对这一 TODO 而言，这条缺口**必须先补**——
"手机当麦克风"同样依赖手机侧真的把采集数据推出来。
