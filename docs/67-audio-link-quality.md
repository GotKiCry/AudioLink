# 音频链路读数与持续 Wi-Fi 抖动

后续更新：本文记录该轮的 30 秒降档策略；当前已改为 5 秒，并加入 Android 全链水位反馈与积压回收，见 [docs/69](69-playout-latency-recovery.md)。

## 问题与实现

此前桌面摘要在窄窗口会被隐藏，设备卡片没有质量读数；遥测桥接又以 `e2e_latency_us > 0` 判定反馈有效。生产跨设备路径没有端到端测量样本，因此真实的接收端丢包、水位和欠载可能被忽略。事件没有 NodeId，原先全局单槽反馈还会让多台设备的数据串线。

现在桌面设备卡片直接显示网络延迟（RTT）、音频丢包率、累计欠载和缓冲水位，工具栏在窄窗口换行保留摘要。Android 接收面板把原来没有数据的端到端读数换成实测网络 RTT，丢包率保留两位小数。双端中英文文案同步。

桌面根据收发方向取数：接收方向使用本机统计，发送方向按 NodeId 查询对应接收端反馈。引擎新增 `fresh_peer_stats`，三秒未更新的反馈不再作为当前读数；接收端当前没有音频数据时也显示占位。`PeerView.quality` 是可空对象，其字段可空；`TelemetryView.receiverReport` 表示反馈是否有效。没有端到端测量时只把端到端相关读数显示为「—」，不隐藏 RTT 和丢包率。网络协议及 UniFFI 结构未变；CSV 保留原来的列。

## 指标口径

| 指标 | 含义 |
|---|---|
| 网络延迟（RTT） | QUIC 测得的网络往返时间，不包含采集、编解码和播放缓冲，不是端到端音频延迟 |
| 音频丢包率 | 接收端最近一秒，在冗余和重传恢复后仍确认缺失的音频包占比；有效零值显示 `0.00%` |
| 欠载 | 到播放截止时没有可用音频的累计拍数，包括错过的播放拍；主动补水不作为新的欠载 |
| 缓冲水位 | 已解码待播 PCM 队列水位，不包含硬件输出缓冲 |

迟到和播放欠载独立于网络序号缺口，不能把 0% 丢包解释为没有断音。完全断流时，序号丢失在后续包到达后才能确认；没有当前接收数据则使用占位，不声称零丢包。

## 连续性改动与取舍

旧自适应上限为三帧，默认帧长下只有 60 ms，无法吸收超过此余量的成批到包。上限提高为六帧（默认 20 ms 帧长下 120 ms）；P95 抖动超过一帧时按 `ceil(P95 / 帧长) + 1` 选择余量。起步仍为一帧，稳定三十秒后每次下降一帧。三帧时的一帧重排窗口不随新上限后移。

主动补水的 Hold 仍输出掩盖音频，但不再增加 `underruns`，否则 1 Hz 控制器会把自己的补水当作新欠载而反复升档。原始欠载、晚到和丢包计数保留。预约播放仍由 epoch 控制，不允许单端缓冲升档改变组内时间线。

弱网缓冲会增加延迟；真正丢失的声音无法由补音还原。与 docs/65 的欠载总数不宜直接作性能比值，因为该文当时还把主动补水计入欠载。

## 验证

- 新增实际播放线程回归：每 80 ms 成批送达四帧，三帧初始余量出现欠载；六帧余量零欠载，所有输出样本保留原值。
- 自适应测试覆盖 70 ms 抖动、六帧上限与逐档恢复；短缺口测试确认真实欠载仍计数、主动补水不重复计数。
- 桌面测试覆盖没有端到端样本仍显示网络数据、两台设备反馈隔离、有效零丢包、未上报占位、停止或测量缺失后不沿用旧分位值。
- Android 映射测试覆盖没有端到端测量仍传递 RTT 和丢包率。
- Playwright 使用模拟 IPC 数据检查 1024×640 深色及 1440×900 浅色窗口：设备卡片与工具栏指标可见，无横向溢出、无页面异常。截图及结果在 `target/evidence/quality-*.png`、`quality-visual.json`。模拟数据仅用于布局验证。
- `cargo fmt --all --check`、内核和桌面全目标 Clippy 通过；完整内核 nextest **551 通过、2 跳过**；桌面 Rust **50 通过、1 忽略**；前端 **177 通过**，生产构建通过。
- `npm run tauri:dev` 无额外环境变量启动成功，窗口 `AudioLink` 正常响应，前端 HTTP 200。验证后已停止本次启动的进程树。
- 30 秒弱网注入：2% 丢包、15±15 ms 延迟、5000 kbps、种子 1，通过现有弱网门槛；4 次欠载、1 次解码补音、4 次迟到，注入侧丢弃 61 个数据报。该门槛不等价于真实听感无损。报告在 `target/evidence/quality-wifi.json`。末次实际队列水位 160 ms：六帧是控制器目标上限，成批到达可短时超过目标，不能把 120 ms 宣称为实际水位硬上限。
- Android 双 ABI 原生库 release 与 `assembleDebug` 构建通过，JVM 单元测试 **238 通过**。两份 APK 在 `android/app/build/outputs/apk/debug/app-arm64-v8a-debug.apk` 与 `app-armeabi-v7a-debug.apk`，已核对源原生库→合并库、剥离库→APK 内文件的 SHA-256，确认包含本次内核。结果在 `target/evidence/quality-android-artifacts.json`。
