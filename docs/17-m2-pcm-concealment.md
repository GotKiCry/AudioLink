# M2 自建 PCM 丢包掩盖

> 日期：2026-09-16  
> 范围：CELT-only 接收路径的重复上一帧、淡出、恢复交叉淡化，以及序号/遥测接线

## 1. 问题与裁决

项目默认使用 48 kHz、立体声、20 ms、160 kbps、`RESTRICTED_LOWDELAY`，实际编码模式为 CELT-only。
`opus-rs` 在这个模式下无法提供可依赖的连续丢包掩盖：第二个丢失帧起会进入硬静音，真实包回来时还有明显能量凹陷。

`opus-rs` 也不公开每包最终使用的 SILK / Hybrid / CELT 模式。仅凭 `Application::Audio` 判断“有真 PLC”并不可靠，
因为本项目的高码率 Audio 档同样会选择 CELT。开发回归中，连续调用 6 次原生 conceal 后，恢复包 RMS 只剩约 0.002；
跳过未经证明的原生 conceal 后，恢复包 RMS 回到 0.02 以上。因此 `OpusDecoder::concealment_is_real()` 目前对所有支持档位
都保守返回 `false`，接收路径统一使用自建 PCM 掩盖。将来只有获得可靠的模式 getter 或逐包 ToC 判定后，才可开放原生路径。

## 2. 实现

`audiolink-audio::PcmConcealer` 保存上一帧成功解码的立体声 PCM，所有工作缓冲在构造时分配：

- 丢一帧时重复上一帧，帧边界用每声道 120 个样本（2.5 ms）平滑衔接；
- 连续丢包按时间线性衰减，120 ms 后进入静音；
- 真实音频恢复时，将上一帧掩盖输出与恢复帧首 2.5 ms 交叉淡化；
- 新流、异常大序号跳变和显式复位都会清除旧历史，避免跨流泄漏音频。

接收侧 `AudioReceiver` 把 Opus 解码器、PCM 掩盖历史和期望序号放在同一个状态对象中：

- 小序号空洞先生成对应序号的掩盖帧，再提交当前真实帧；
- 迟到或重复包在解码前丢弃，避免污染 Opus 状态和播放时间轴；
- 解码失败时也为当前序号生成一帧 PCM 掩盖；
- 单次空洞最多生成 120 ms 掩盖帧，剩余时间由播放时钟补静音，并重建 Opus 状态，避免长空洞塞满待播队列；
- 20 秒以上的序号跳变视为时间轴重建，以当前包为新基准；
- `expected`、`lost`、`plc`、`late_drops` 按一次接收结果批量记账。

## 3. 自动回归

测试使用真实 `OpusEncoder` / `OpusDecoder`，覆盖：

| 场景 | 断言 |
|---|---|
| 单包丢失后迟到包到达 | 输出序号连续，掩盖帧非静音；迟到包不再进入解码器 |
| 空载荷解码失败 + `u32` 回绕 | 当前序号由 PCM 掩盖补齐，时间轴连续 |
| 201 包中固定丢 4 包（约 2%） | 输出仍为 0...200；`lost=plc=4`；4 个丢失序号 RMS 均大于 0.02 |
| 连续丢 6 帧（120 ms） | 能量单调淡出、120 ms 内不提前硬切；真实包恢复 RMS 大于 0.02 |
| 999 帧长空洞 | 只生成 6 帧掩盖和当前真实帧，不把 999 帧全部压入队列 |
| 掩盖器单元测试 | 无历史/错误长度、淡出、恢复交叉淡化、立体声独立与复位 |

这里的约 2% 丢包是接收器级确定性注入，用于固定序号、解码和 PCM 行为；它不是网络代理或 Wi-Fi 弱网验收。

## 4. PHK110 正常链路回归

最终双 ABI Release APK 已安装到 PHK110（Android 16 / API 36），并从设备回拉逐字节核对：

- APK SHA-256：`b51180b4bb208ae273d4eb2bccb66e6728375fbafffa219c31dd13b2b05da2e7`；
- V2 签名通过，本地 APK 与设备回拉 APK 哈希一致；
- 60 s 真实 PC→PHK110 QUIC/mTLS/Opus 合成音链路退出码 0；
- 对端待播队列 P50/P95/P99/max 均为 40 ms，链路丢包 0%，`plc=0`，码率末值 160.4 kbps；
- Android 为 `LOW_LATENCY`、48 kHz、2 ch；AudioLink 活跃 AudioTrack 的 underrun 为 0，写入错误为 0；
- 引擎欠载/迟到从 2 增至 49，仍属于已有的到达/调度抖动问题，交给下一项自适应抖动缓冲处理。

测试结束后已停止手机服务。该回归证明自建掩盖没有破坏正常链路，不能替代 5 Mbps / 2% 丢包 / 30 ms 抖动的 M2 弱网验收。
