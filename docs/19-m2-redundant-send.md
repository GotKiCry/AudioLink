# M2 默认冗余双发与同档补水恢复

日期：2026-09-16

## 1. 交付范围

发送端默认对每个 Opus 音频帧发送两个副本：

- 当前帧先作为主包发送；到下一帧时，先发送新的主包，再发送上一帧副本；
- 同一序号的两个副本因此至少相隔一个 20 ms 包时距，主包没有新增等待；
- 副本保持 `ptype=AUDIO`，并设置 `FEC_REDUNDANT`；主包不设置该标志；
- `record_expected` 只按主包计一次，实际链路码率按两个数据报都计入。

接收端的有界乱序窗记录近期已交付序号，并与待排序序号一起去重。主包或副本谁先到就采用谁；另一个副本静默丢弃，不进入 `late_drops`。到达抖动也只使用每个序号的首个有效副本，因此背靠背到达的副本不会制造虚假的约 20 ms jitter。

近期已交付窗口保留 6 个序号，是默认副本延迟 1 帧和现有最多 3 帧乱序窗的两倍。超出该窗口且已经越过播放游标的未知旧包仍按真实迟到处理，不能借“副本”语义隐藏异常流量。

## 2. 同档补水修复

首轮 PHK110 90 s 回归在约第 53 秒暴露了已有自适应状态机的边界：目标已经是最高 60 ms 时，一次欠载无法再通过“升档”触发补水。播放游标领先发送序列后，后续帧会持续迟到，首轮最终欠载/迟到达到 1981/1574。

播放线程现在把“目标档位”和“当前真实余量”分开处理：

- 欠载后标记需要同档补水；
- 只有队列重新出现真实帧时才按当前目标深度 Hold，避免完全断流时反复补静音并冻结时间轴；
- 已在 60 ms 最高档也能重新建立余量，不依赖再升一级；
- 达到目标水位可提前结束 Hold，等待次数仍受 1--3 帧目标约束。

## 3. 自动回归

新增回归覆盖：

| 场景 | 断言 |
|---|---|
| 主包 1 丢失，按 `0, 0副本, 2, 1副本, 3, 2副本` 到达 | 真实 Opus 只解码 `0, 1, 2, 3`；loss / PLC / late 均为 0 |
| 已交付副本再次到达 | 静默去重，不增加 `late_drops` |
| 待排序序号的副本再次到达 | 不占第二个乱序槽，不挤掉有效包 |
| 60 ms 最高档发生欠载 | 无需再次升档即可按真实缺口补水并恢复 |
| 播放 sink 停顿 250 ms | 真 QUIC/Opus 链路恢复，后续延迟 P95 低于 100 ms |

PC 双 Engine 真 QUIC 20 s 回归中，接收码率稳定在 320.8 kbps，丢包、PLC、欠载和迟到均为 0；帧封口到 sink 写出的 P50/P95 为 20.48/20.73 ms，接收 jitter P50/P95 为 0.15/0.51 ms。

## 5. 边界与后续

本阶段证明默认双发能在正常 Wi-Fi 上把实际码率稳定提升到约 320 kbps，且重复副本不会改变唯一播放序列或污染丢包、PLC、迟到和 jitter 口径。真实 5 Mbps / 2% 丢包 / 30 ms 抖动注入仍属于 M2 父任务，不能用正常链路结果替代。

下一项实现 RTT < 30 ms 时的 NACK 辅助重传，包括发送端 1 s 帧缓存、接收端缺口请求、10 ms 重试间隔与最多 5 次边界。M2 父任务保持 In Progress。
