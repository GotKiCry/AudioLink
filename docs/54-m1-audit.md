## 2. 挑出的错

### A. 对前提的更正（重要，方向与怀疑相反）

**`[M1] 验收` 主行没有声称完成。**我按字符核过：该行 541 字符，`含「完成」= False`、`含「2026-09-17」= False`、`含「latency_budget」= False`；正文反而明确写着「**尚未完整测量**」「**因此保持 In Progress**」。
你描述的那段「2026-09-17 说完成 + 又说不能用来宣称验收通过」**在 `[质量] 端到端延迟回归护栏` 这条 Done 条目里**（我核过：该行 `含 2026-09-17 = True`、`含 完成 = True`、`含「不能用来宣称」= True`）。它的「完成」是**护栏这一条**完成 —— 让「代码改动导致的延迟退化」不再依赖人的记忆；同段又写清「回环 ≠ 真机、40 ms 不能宣称验收通过」。
→ 所以 `[M1]` 的现状**不是「不清楚」，而是「清楚且自洽」**：验收线未达成、主行正确保持 In Progress、真机项由 55 行接住。这一点与 M3/M4/M5 那几次（正文漏记/活数字腐烂）**性质不同**。

### B. 真错：`docs/12` 的「30 min 无断流 ✅」未标注「修复前」（过时风险）

`docs/12` §0 表与 §5.1 记的 30 min 长跑是**待播队列修复之前**的版本（同表自己写着「水位顶到 320 ms 上限、迟到丢弃 53、欠载 7→69」）。修复之后（`docs/16`：队列降到 40/40/60 ms）**没有再跑过 30 min**。这两处**没有标注「修复前」**，读者会把它当成现状 —— 与看板 55 行「仍缺修复后 30 min 长跑」直接对不上。
→ 处置建议：在 `docs/12` 这两处加一行「修复前版本；修复后 30 min 未跑（见 docs/16 与看板 55 行）」。

### C. 口径混淆风险：两个都叫「e2e 下限」的数字

`docs/16`「≈73 ms」与 `docs/12`「≥115 ms」**不是矛盾**，但都没有标口径：前者是**队列修复后、不含设备输出**的模型下限；后者是**修复前 run3** 的实测下限（账本里已含播放环水位 80 ms）。建议两处都补上「修复前/后 + 含不含设备输出」。

### D. 活数字漂移（不算错，但值得知道）

护栏基线与测试注释记的是 **P50 40 615 µs / P95 41 007 µs**（`docs/47` §3 与 `latency_budget.rs` 的常量注释）；我**今天实测 P50 44 543 µs / P95 44 919 µs**（soak 同时在跑）。阈值 80 ms / 150 ms 仍有 **1.8× / 3.3×** 余量 → **护栏健康**，属负载相关漂移，不必改数字。

### E. 无自动化证据的项（不阻塞，但要标清）

真机侧的**全部**读数（低延迟模式、待播队列、PCM 环、30 min 无断流、四轮断流）都是**人工采集**的 adb/遥测读数，没有脚本化、可重放的证据；护栏覆盖的只是回环。这不是缺陷（真机测量本就如此），但任何"验收达成"的结论都必须建立在这批人工读数 + 一次新的声学测量上。

## 3. 明判：能否判 Done（含「实现完成」与「验收线达成」的区分）

### 3.1 实现完成：**是**

| M1 的三条硬指标 / 验收项 | 状态 |
|---|---|
| 零重采样 | ✅ 断言 + 7 项单测 + 真机读数（`PCM_FLOAT` / 48000 / 2ch） |
| 低延迟模式生效 | ✅ 真机读数（`LOW_LATENCY` + `FAST` + FastMixer） |
| 链路可用性 / 断流 / 出声 | ✅ 真机四轮 + 30 min（修复前版本；当轮另含 PIN 配对验收，该机制已随本轮移除）|
| 「接收侧待播队列持续增长」这个听感缺陷 | ✅ 已修（队列 240/300/320 → 40/40/60 ms，有真机前后对照）|

### 3.2 验收线达成：**否**

1. **两个核心数字（P50 ≤ 110 / P95 ≤ 150）从未被真机声学测量。**真机测的是分段：播放环水位 80 ms、AudioTrack 缓冲 3844 帧 = 80.08 ms（flinger track latency 101 ms）、网络单向 5.86 ms（模型）、解码 0.06 ms（**本机替代值**，对端真值未导出）。
2. **已有相反证据，不是「未知」：**`docs/12` §0 表写明 `e2e P50 ≤ 110 ms ❌ 当前不满足（实测下限 ≥ 115 ms）`；修复后按 `docs/16` 的模型重算，下限 ≈73 ms **再叠加设备输出 80 ms ≈ 153 ms**，仍超 110 ms。
3. 回环护栏**不能**填补这个空缺，而且它**自己声明了这一点**（`docs/47` §4「回环 ≠ 真机…40 ms 不能用来宣称『M1 验收通过』」；`docs/47` §6「真机延迟仍在人工验收清单里，本护栏不替代它」）。

### 3.3 为什么**不能**机械套用 M3/M4/M5 的口径

M3/M4/M5 判 Done 的共同结构是：**核心判据能在回环/本机达成且余量巨大（或本身就是产物与流程）**，真机项只是**追加验证**。

- M3 组内 ±10 ms：回环 P95 0.03 ms（比验收线低 **5 个数量级**）→ 真机项是「用扬声器波形复核」；
- M4：能力协商/混音有回环端到端证据，真机项是「听感与真机清单」；
- M5：验收大多是**产物与流程**（APK 尺寸与签名、便携包哈希、许可证清单），本机就能复核。

**M1 的核心判据在回环上根本不可达**：回环 44 ms 没有 Wi-Fi 抖动、没有扬声器缓冲、没有 AudioTrack 路径；真机账本 ≈195 ms（修复后 ≈153 ms），**差 3.5～4.4 倍**。因此「真机项由独立条目承接」在这里**等于把验收线本身外包出去** —— 55 行接住的正是 P50/P95 这两个数字。

→ **结论：`[M1]` 验收不能判 Done。**这是「验收未达成」，不是「实现完成、余项已承接」。

### 3.4 还差什么（具体、可执行）

1. **一次真机声学端到端 P50/P95 测量**（当前**零**）：PC 播脉冲 → 手机录音（或反向），量法可借鉴 `tools/sync-measure` 的脉冲对齐思路；这一项不做，「达标」永远只是推断。
2. **修复后的 30 min 长跑**（看板 52/55 与 `docs/16` 都写明未做；`docs/12` 的那次是修复前）。
3. **先拧两个旋钮，否则测了也不达标**：对端播放环水位 80 ms（`PRIME_FRAMES` / `PLAYBACK_QUEUE_FRAMES`）、对端 AudioTrack 实际缓冲（**请求 960 帧、实际生效 3844 帧 = 80 ms**）。两处都是工程旋钮而不是物理限制（见 `docs/12` §3 结尾）。
4. **文档层面的两条小修**：`docs/12` 的 30 min 表标注「修复前」；两个「e2e 下限」补口径（修复前/后 + 含不含设备输出）。
5. **可选**：把主行 52 行的「段模型下限约 73 ms」后面补一句「**不含**设备输出 80 ms，因此不等于验收线」——避免被读成「已经很接近 110 ms」。
