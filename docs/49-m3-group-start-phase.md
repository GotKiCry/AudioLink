# M3 组内起播相位：偶发差一整帧（回环复现约 20～40%）

> 发现日期：2026-09-17 ｜ 触发：CI run `35151576499` 的 `core-heavy` 失败 ｜ 测试：`group_sync::two_receivers_play_the_same_frame_within_ten_milliseconds`

## 1. 现象与实测数字

CI 失败时的打印（`[group-sync]`）：

```text
[group-sync] 绝对偏差（含起播差）：样本 247 · P50 19.98 ms · P95 20.38 ms
[group-sync] 扣掉起播差后（偏移 1 帧）：样本 247 · P50 0.01 ms · P95 0.02 ms
组内偏差 P95 = 20.38 ms 超过验收线 10 ms（两端播放同一帧的时刻差，含起播差）
```

两个数字合起来说明的事很清楚：**排播本身是准的**（扣掉起播差后 0.02 ms），差的**只有起播**——一端比另一端整整晚**一帧（20 ms）**。

复现率（同一份代码、本机与 CI）：

| 环境 | 次数 | 失败 |
|---|---|---|
| CI（core-heavy，384 个测试并行） | 4 | 1 |
| 本机（engine 套件 27 个测试并行） | 12 | 2（集中在同一次采样里） |
| 本机（单跑这一条） | 3 | 0 |

结论：不是噪声，也不是单机环境问题，而是**负载相关、约 20～40% 概率**的真实缺陷。重跑即绿恰恰说明它是相位竞争，而不是逻辑必然。

## 2. 根因：网格锚点只固定了「相位」，没固定「哪一格」

`runtime.rs` 播放线程的起播锚点（2026-09-17 的第一层修复）是：

```rust
let frame_us = frame_ms.max(1) * 1_000;
let remainder = now_monotonic_us() % frame_us;
next_write = Instant::now() + Duration::from_micros(frame_us - remainder);
```

它把拍点锚到全局帧网格（`now_monotonic_us()` 的 `frame_us` 整数倍），**两端确实落在同一张网格上** —— 这一层是对的，
它解决的是「相位各不相同」。但它没有解决**「两端各自落在哪个网格点」**：

设两端完成攒帧、进入这一分支的时刻相差 Δ（回环实测几毫秒，取决于配对 → 建组 → 开流 → 攒够目标帧数的先后）：

- 若 A、B 之间**没有**跨过网格边界：`remainder_B = remainder_A + Δ`，两端的 `now + (frame_us - remainder)` 指向**同一个**边界 ✔
- 若 A、B 之间**跨过**了边界：`remainder_B = remainder_A + Δ − frame_us`，两端指向**相邻的两个**边界 ✘ —— 起播差一帧

也就是说，起播是否一致取决于「两端的准备时刻之间有没有恰好夹着一个网格边界」。
Δ ≈ 4～8 ms、网格间距 20 ms ⇒ 踩中概率 ≈ Δ / frame_us ≈ **20～40%** —— 与上表的复现率吻合。

## 3. 为什么这不是「护栏太严」

`docs/33-m3-multi-session.md` §7.5 记录的第一层修复（判定比微秒 → 比帧对齐边界）与第二层修复（拍点锚到网格）都还成立：
它们把 `aligned`（扣掉起播差）压到了 0.01 ms，也把判定精度问题解决了。

但 M3 验收线是 `absolute_p95 ≤ 10 ms`（**含起播差**），而组内同步的语义本来就是「两台设备在同一时刻播同一帧」——
起播差一帧不是测量误差，是**听得出来的一帧错位**。所以断言不该放宽，该修的是起播锚点。

## 4. 修法：让拍点与判定**同源**（已实施 2026-09-17）

真正的根因不在「取整方式」，而在**参考系**：拍点锚在全局帧网格（相位 0），target 又被向上取整到同一个
全局网格 —— 两端的时钟估计只差 ε，同一帧的 target 就相差 ε，各自取整后便可能落到**相邻两格**。

（本文档第一版把修法押在「向上取整改成贴近最近边界」上。那个分析不彻底：snap 只是把决策的跳变点从帧边界
挪到半帧处，跨界概率仍是 ε / frame，治不了根。此处更正。）

修法三步，全部已实施：

1. `EpochSchedule::target_us`：**不再做任何网格对齐**，直接给 epoch + lead + 样本偏移（`epoch.rs`）；
2. 新增 `EpochSchedule::phase_us(sample_index, offset_us, frame_samples)`：相位由**该帧的 target** 算出
   —— 必须传真实序号，实际流的样本序号由首包给出，不能假设它对齐到某个网格；
3. 播放线程起拍锚点 `playout_start_anchor`（`runtime.rs`）：有排播时**首拍直接落在待播帧的 target 上**，
   没有排播时才退回全局网格（相位 0）。

于是两端的首拍只差各自的 ε（回环约 2 ms），此后每拍 +frame 与 target 序列同步，而不是「0 或整整一帧」。

### 4.1 两次尝试（记账：第一次不够，别重复走）

- **第一次：把拍点锚到「该帧 target 的相位」**（不够）。20 轮采样后仍有失败轮，失败样本依旧是
  P50 20.04 ms / 偏移 1 帧。原因：相位锚点取的是「下一个相位节拍」，而它可能落在 target **之前** ——
  这一端要多等一拍（+20 ms）才播，另一端恰好 ≥ target 立刻播，于是还是差一帧。
- **第二次：直接令首拍 = target**（若已过期则立刻播）。

顺带清掉了 `action` 里已无人使用的 `frame_samples` 参数（迟到门限本就按 µs 算，与帧长无关）。

## 5. 验证

### 5.1 单测（`epoch.rs`，13 项全绿）

- `target_sits_exactly_on_the_epoch_phase_grid`：ε 取 0 / ±2 ms / 1.337 ms，序号同时覆盖帧整数倍与
  **非整数倍**（44 640 = 46.5 帧），断言 target 恒落在本端拍点上；
- `both_ends_play_the_same_frame_within_the_clock_estimate_error`：两端 ε 相差 2 ms，逐拍断言「都判播」
  且播放时刻之差 ≤ ε；
- `target_is_played_on_the_tick_that_reaches_it`：未到目标等待、到点即播。

### 5.2 回环实测（单次全套 27 项全绿）

`[group-sync]` 绝对偏差 **P50 0.00 ms · P95 0.02 ms（偏移 0 帧）**，扣帧后同为 0.00 / 0.02 ms ——
修复前同一处是 19.98 / 20.38 ms（偏移 1 帧）。

### 5.3 复现率采样（每轮 = engine 套件 27 项；期间本机 8 h soak 一直在跑）

```text
cd core
cargo nextest run -p audiolink-engine --test engine --no-fail-fast   # 连跑 20 轮
```

| 版本 | 失败轮 | 失败测试 |
|---|---|---|
| 修复前基线（12 轮） | 2 / 12（17%） | `group_sync` |
| ① 拍点锚「该帧 target 的相位」 | 10 / 20（50%） | `group_sync` |
| ② ① + 首拍直接锚 target | 6 / 20（30%） | `group_sync` |
| ③ ② + 2 ms 早起容差 | 4 / 20（20%） | `group_sync` |
| ④ ③ + 排播模式禁用升档 Hold | 5 / 20（25%） | `group_sync` |

原始记录：`target/evidence/group-sync-20rounds-v2.txt`（②）、`-v3.txt`（③）、`-v4.txt`（④）。

**结论（诚实记账）**：三次改动各自消除了一个**真实机制** —— ①③④ 分别在单测/单次实测里起效 ——
但叠加之后失败率仍在 20~25% 之间波动，**没有收敛到 0**。这说明至少还有一条未被识别的机制，
或者当前采样环境（8 h soak 占着 CPU 与回环、27 项测试并行、2 核 CI 级负载）本身贡献了不可忽略的噪声。

**关键对照（本轮已做，推翻了「并行竞争」这条假说）**：把这条测试**单独**跑 30 次（去掉 27 项测试互相争抢）
仍是 **6 / 30 失败（20%）**，失败形态与并行时一模一样（P50 19.98~20.03 ms / P95 20.4~20.6 ms；成功时
P50 0.00 / P95 0.03~0.05）。也就是说：**并行竞争不是原因**，20% 是这条链路真实的独立失败概率，
四次采样之间的「改善」很可能都是噪声。

**下一步（按优先级）**：

1. **第一嫌疑：排播可能在起拍之后才生效**。测试流程是 `start_send_many` 先跑、`GROUP_EPOCH` 随后到达；
   若播放线程已经按「全局帧网格」起拍，之后 target 与拍点就不同相 —— 一部分帧因此判 Wait、白等一拍，
   整段就差一帧。修法方向：schedule **首次生效**时重新锚定拍点（把 `next_write` 重置到当前待播帧的 target）。
   验证方式：单跑 30 次（当前基线 6 / 30）；
2. 抓失败样本时**同时打印两端的排播遥测**（`EngineEvent::PlayoutScheduled` 的 `target_local_us`、
   各自的 underrun / late_drop / 缓冲档位），把「整段差一帧」定位到具体哪一侧、哪一拍；
3. 排查剩余的「两端首帧不同」路径（首包丢失/乱序导致 `PlayoutSync.base` 不同 → 各自锚到不同帧的 target）。

### 5.4 第 57 轮诊断：偏移发生在**起拍那一拍**，第 5 个机制尝试无效

给测试加了两个诊断量（`[group-sync][diag]`）：两端各自的**写入次数**，以及「第 k 次写出」差值首次超过
10 ms 的位置 k。失败样本（20 轮里的第 5 轮）：

```text
[group-sync][diag] A 写入 298 次 · B 写入 297 次 · 首次偏离>10ms：Some((0, 19.95 ms))
[group-sync] 绝对偏差（含起播差）：样本 247 · P50 20.00 ms · P95 20.42 ms
[group-sync] 扣掉起播差后（偏移 -1 帧）：样本 247 · P50 0.00 ms · P95 0.03 ms
```

两个结论：

1. **k = 0** —— 偏移从**第一次写出**就存在，不是中途漂移，也不是运行中丢帧/重缓冲补拍的累积；
2. 两端写入次数只差 1（298 vs 297）—— 不是某一端普遍多写或少写，而是**起拍整体晚了一拍**。

同轮还试了第 5 个机制（给 `PlayoutSync` 加 `generation`，排播生效时重锚拍点）：单跑 30 次 **8 / 30** 失败，
与基线 6 / 30 没有显著差别 —— 已回退，不留无益复杂度。至此五个机制假设（相位锚定 / 锚 target / 早起容差 /
排播禁升档 / 生效重锚）全都被数据否掉，失败率始终在 20~27% 徘徊。

**下一步（具体动作，不是方向）**：在诊断里再补三项 —— 两端各自的 `PlayoutSync.base`（首帧样本序号）、
起拍那一刻的 `next_write` 与首帧 `target_us`、以及 `PlayoutScheduled` 事件的 `wait_us`。
「起拍晚一拍」最可能的原因是**两端用于锚定的首帧不是同一帧**：`playout_start_anchor` 取的是队列里**当前最旧**的一帧，
而真正的首帧可能还在网络上（数据报到达顺序不保证）—— 补上这三项就能直接判定。
### 5.5 第 58 轮突破：**排播根本没有生效**（前六个机制假设全都问错了问题）

本轮把诊断做到「这一端到底有没有进过排播」这一层：加了 `PlayoutScheduled` 事件的打印
（`drain_scheduled`）—— 该事件只在**首次进入排播**时报一次，是「有没有走排播」的直接证据。失败样本：

```text
[group-sync][diag] 排播事件 A=[] · B=[]
[group-sync][diag] A 写入 297 次（首个音频 #Some(0)）· B 写入 298 次（首个音频 #Some(0)）· 首次偏离>10ms：Some((0, 19.91))
[group-sync] 绝对偏差（含起播差）：样本 247 · P50 20.03 ms · P95 20.38 ms
[group-sync] 扣掉起播差后（偏移 1 帧）：样本 247 · P50 0.00 ms · P95 0.03 ms
```

**两端都没有排播事件** —— 它们从头到尾走的是「本地游标」路径（队列攒够帧就播），起拍时刻由各自的到达时序
决定，所以偶尔差一帧、而 `aligned` 始终 0.00 ms。前面几轮还确认了：两端**首个音频都在 #0**（不是静音补拍）。

根因是**产品缺陷**，不在测试里：`GROUP_EPOCH` 常常**早于开流**到达，而 `handle_control` 的
`ControlRequest::GroupEpoch` 分支只有在 `playback` 已存在时才 `set_schedule`，否则**静默跳过**
（`runtime.rs` 3351 行附近那个 `if let Some(handle) = playback.as_ref()`）。测试流程恰恰是
`create_group` → `start_send_many`，于是排播经常在播放线程创建之前到达并被丢掉 —— 20% 的复现率
就是这场时序竞争的概率。

**这解释了前六个机制假设为何全都不动失败率**：它们改的都是排播内部的逻辑，而排播压根没跑起来。

**对既有结论的影响（必须记账）**：

- `[M3] 组内同步回环护栏`（Done）此前测到的是「两个本地游标播放器」的相位差，**不是** epoch 排播的同步质量；
  该护栏必须在排播真正生效后重测，结论才作数；
- 同一批次改的三处（target 不再全局网格对齐、首拍锚 target、2 ms 早起容差）在排播不生效的背景下无法验证效果，
  修复后需要复测；
- 本轮另把起拍锚点从「队列里当前最旧的一帧」改成「本流首帧」（`PlayoutSync.base`）—— 这一步逻辑上更稳
  （与到达顺序无关），但它的收益同样要等排播生效后才能测出来。

**下一步（修复方案，下轮执行）**：把排播**缓存**到播放句柄就绪再应用 —— `PeerSession` 上加一个
「待应用排播」槽位（`epoch_id` / `epoch_local_us` / `lead_ms`），`GroupEpoch` 分支在 `playback` 为 None 时存进去，
`OpenStream` 创建播放句柄后立刻应用；显式 API `Engine::schedule_playout` 同样处理（它现在返回 `cap_unsupported`，
语义也不对）。验证：`[group-sync][diag] 排播事件` 必须两端非空，且单跑 30 次的失败率应降到 0（当前 5~8 / 30）。
### 5.6 第 59 轮：修好了 —— 排播首次真正生效

修法三处一起做：

1. `PeerSession` 新增「待应用组基准」槽位 `pending_schedule`；
2. 新增四个小函数 `apply_schedule` / `stash_schedule` / `take_stashed_schedule` / `clear_stashed_schedule`，
   把「有播放句柄就应用、没有就暂存」这条原则集中到一处；
3. 三处控制路径统一走它，外加开流后补应用：
   - `ControlRequest::GroupCreate` —— **这才是测试与真实流程实际走的路径**（`create_group` 只发 GROUP_CREATE，
     `GROUP_EPOCH` 仅用于动态加入），第 58 轮只改了 `GroupEpoch` 分支，所以排播事件仍然是空的；
   - `ControlRequest::GroupEpoch`；
   - `SessionCommand::SchedulePlayout` —— 显式 API 不再回 `cap_unsupported`（「先建组、再推流」是正常用法）；
   - `ControlRequest::OpenStream` —— 建好播放句柄后立刻补应用暂存的那份。

**实测（单跑 30 轮）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 失败轮 | 5 ~ 8 / 30 | **0 / 30** |
| 排播事件非空 | 0 / 30 | **30 / 30** |
| 绝对偏差 | 偶发 P50 ≈ 20 ms | P50 0.00 ms · P95 0.02~0.05 ms |

排播生效后两端拿到的 `target_local_us` **完全相同**（例如两侧都是 130647 µs）—— 这正是「两台设备在同一时刻
播同一帧」所需要的前提，此前从未成立过。引擎全套无回归：集成 27 项 + 单测 150 项全绿。

同批次改的三处（target 不再做全局网格对齐、首拍锚 target、2 ms 早起容差）是在这一步**之后**才第一次被真正检验 ——
它们此前的「无效」是因为排播没跑起来，不是因为它们错。

**教训（写给自己）**：连续六次改「机制」都不动失败率时，就该往上一层问一句「这段代码到底被执行了吗」。
本次的决定性证据不是任何一次代码改动，而是 `[group-sync][diag] 排播事件 A=[] · B=[]` 这半行打印。
