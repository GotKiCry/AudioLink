# M3 组内起播相位：偶发差一整帧（回环复现约 20～40%）

> 发现日期：2026-09-17 ｜ 触发：CI run `35151576499` 的 `core-heavy` 失败 ｜ 测试：`group_sync::two_receivers_play_the_same_frame_within_ten_milliseconds`

## 1. 现象与实测数字

CI 失败时的打印（`[group-sync]`）：

```text
[group-sync] 绝对偏差（含起播差）：样本 247 · P50 19.98 ms · P95 20.38 ms
[group-sync] 扣掉起播差后（偏移 1 帧）：样本 247 · P50 0.01 ms · P95 0.02 ms
组内偏差 P95 = 20.38 ms 超过验收线 10 ms（两端播放同一帧的时刻差，含起播差）
```

两个数字合起来说明的事很清楚：**排播本身是准的**（扣掉起播差后 0.02 ms），差的**只有起播**——一端比另一端整整晚**一帧（20 ms）**。

复现率（同一份代码、本机与 CI）：

| 环境 | 次数 | 失败 |
|---|---|---|
| CI（core-heavy，384 个测试并行） | 4 | 1 |
| 本机（engine 套件 27 个测试并行） | 12 | 2（集中在同一次采样里） |
| 本机（单跑这一条） | 3 | 0 |

结论：不是噪声，也不是单机环境问题，而是**负载相关、约 20～40% 概率**的真实缺陷。重跑即绿恰恰说明它是相位竞争，而不是逻辑必然。

## 2. 根因：网格锚点只固定了「相位」，没固定「哪一格」

`runtime.rs` 播放线程的起播锚点（2026-09-17 的第一层修复）是：

```rust
let frame_us = frame_ms.max(1) * 1_000;
let remainder = now_monotonic_us() % frame_us;
next_write = Instant::now() + Duration::from_micros(frame_us - remainder);
```

它把拍点锚到全局帧网格（`now_monotonic_us()` 的 `frame_us` 整数倍），**两端确实落在同一张网格上** —— 这一层是对的，
它解决的是「相位各不相同」。但它没有解决**「两端各自落在哪个网格点」**：

设两端完成攒帧、进入这一分支的时刻相差 Δ（回环实测几毫秒，取决于配对 → 建组 → 开流 → 攒够目标帧数的先后）：

- 若 A、B 之间**没有**跨过网格边界：`remainder_B = remainder_A + Δ`，两端的 `now + (frame_us - remainder)` 指向**同一个**边界 ✔
- 若 A、B 之间**跨过**了边界：`remainder_B = remainder_A + Δ − frame_us`，两端指向**相邻的两个**边界 ✘ —— 起播差一帧

也就是说，起播是否一致取决于「两端的准备时刻之间有没有恰好夹着一个网格边界」。
Δ ≈ 4～8 ms、网格间距 20 ms ⇒ 踩中概率 ≈ Δ / frame_us ≈ **20～40%** —— 与上表的复现率吻合。

## 3. 为什么这不是「护栏太严」

`docs/33-m3-multi-session.md` §7.5 记录的第一层修复（判定比微秒 → 比帧对齐边界）与第二层修复（拍点锚到网格）都还成立：
它们把 `aligned`（扣掉起播差）压到了 0.01 ms，也把判定精度问题解决了。

但 M3 验收线是 `absolute_p95 ≤ 10 ms`（**含起播差**），而组内同步的语义本来就是「两台设备在同一时刻播同一帧」——
起播差一帧不是测量误差，是**听得出来的一帧错位**。所以断言不该放宽，该修的是起播锚点。

## 4. 修法（未实施）

按性价比排序：

1. **首拍锚到 epoch 的绝对目标时刻**（最贴合协议）：协议 §7 给的本来就是「共同基准 + lead」——
   `EpochSchedule::frame_aligned_target_us(sample_index, offset_us, frame_samples)` 算出的 target 对两端是**同一个绝对时刻**，
   与各自的准备时刻无关。播放线程在 `!primed` 分支里若已有 schedule，就应当把它当作首拍锚，而不是「下一个网格边界」。
2. **把 `frame_aligned_target_us` 的取整从「向上取整」改成「贴近最近的边界」**：两端的目标只差时钟估计误差（≤ 2 ms），
   snap 到最近边界后必然落在同一个边界上（2 ms 远小于半帧 10 ms）。这一条与上一条互补：上一条管首拍，这一条管每一拍的判定。
3. 备选：给「距离下一个边界 < 阈值」时再多等一帧。**这个方案无效**（本文档第一版草稿里提出过，已否）：
   跨边界的那一种情形里，两端距离各自的下一个边界都还远，阈值判断不会触发。

## 5. 验证手段

修复前先用**复现率**当基线：

```text
cd core
cargo nextest run -p audiolink-engine --test engine --no-fail-fast   # 连跑 20 轮，统计失败轮数
```

当前基线：12 轮里 2 轮失败（约 17%，与 CI 的 1/4 同量级）。修复后的目标：20 轮 0 失败，且 `absolute_p95 ≤ 10 ms`。
