## 1. 现象（现场实测）

| 时刻 | 累计欠载 | 水位 | 抖动 | RTT | 丢包 |
|---|---|---|---|---|---|
| 12:46 | 21 768 | 100 ms | — | 12–22 ms | 0.00% |
| 12:52 | 33 318 | **160 ms** | — | — | 0.00% |
| 12:57 | 51 660 | **160 ms** | 3.1 ms | 8.0 ms | 0.00% |
| 12:58（10.6 s 两点） | 54 640 → 55 158 | 140→160 | 9.7 ms | 10.6 ms | 0.00% |
| 13:05 | 65 865 | 150 ms | 4.1 ms | 10.0 ms | 0.00% |

速率 0.16 → 32 → **48.8 次/秒**，单调加速。链路干净（丢包 0.00%、抖动 3–10 ms），**水位 150–160 ms 毫无物理必要**。
`PLAYBACK_QUEUE_FRAMES = 16`（`runtime.rs:106`）× 10 ms = **硬上限 160 ms** —— 水位正顶在这个上限上。

## 2. 三张不同的嘴：欠载计数有三个独立来源

这是本次排查最重要的结构性发现：**`underruns` 这个数字由三处写入，语义完全不同**。

### A 线 —— 错过的播放拍（`runtime.rs:4969-4985`）★ 主嫌

```rust
let current = Instant::now();
if primed && current > next_write {
    let missed = current.duration_since(next_write).as_nanos() / period.as_nanos();
    if missed > 0 {
        *seq = seq.wrapping_add(missed);
        telemetry.record_underruns(missed);      // ← 一次记 missed 次
        next_write += period.saturating_mul(missed);
    }
}
```

**判据**：回到循环顶部时 `next_write` 已成过去 ⇒ **上一拍的实际处理耗时 > 帧周期**。这些拍被判定"已经过去"，**跳过并批量记账**。

**定量**：48.8 次/秒 ÷ 100 拍/秒 = **0.488** ⇒ 约 **49% 的拍超时**，平均每拍 ≈ **14.9 ms**（帧周期 10 ms）。

**这条线一成立，下游全部自动解释**：播放速率 ≈ 67 拍/秒、供给 100 帧/秒 ⇒ 每秒积压 33 帧 ⇒ **队列必然涨到顶格**（16 帧）⇒ 引发 B 线。

### B 线 —— 满队列拒收（`runtime.rs:3099-3100` + `3615`）

队列满 ⇒ `try_push` 返回 false ⇒ 帧丢弃并记 `late_drops`。
**但** `AudioReceiver::receive` 在调用 emit **之前**就已推进 `self.expected_seq`（`3615`），而 emit 在 `3628/3660` —— 丢掉的帧不会由接收侧补发，**该序号永久空缺**。

### C 线 —— 游标追赶（`runtime.rs:5498-5502`）

队列头部帧 seq 超前游标（`distance > 0`）时，播放层逐拍越过一格，**每格记一次 `underruns`**，同时 `conceal_playout_frame` 补掩盖音（`5327`）。

## 3. v1 假说及被 codex 推翻的部分（诚实记账）

| v1 结论 | 裁定 | 依据 |
|---|---|---|
| 「一次跳号放大成 `distance` 次，而 `distance` = 队列积压深度 ⇒ 16 倍放大」 | **❌ 撤回** | `distance` 是**队头帧与游标的差**，不是队列长度。丢一个序号、下一帧只超前 1 时 `distance` 就是 1。丢一帧 ⇒ 只多记 **1** 次 |
| 「~3% 供需失配」 | **❌ 撤回** | 建立在上面那个错误推算上 |
| 「D1：追赶型 Missing 是纯记账错误」 | **❌ 撤回** | 该分支确实进入 `conceal_playout_frame`（5327），**这一拍真的没有应播真帧** ⇒ 记 `underruns` 是诚实的 |
| 「D2：三个闸门都以零欠载为收敛条件」 | **❌ 撤回** | 只有 `jitter.rs:134`（自适应降档）查计数。**稳态结算**（`jitter.rs:264`）查**连续超额时间**；**积压回收**（`backlog.rs:37`）查**设备水位 + 500 ms 窗口**。后两者是被 **`Missing` 事件本身**打断的，与计数归类是同一事件的两个后果，**不是独立缺陷** |
| 「M1（只改计数口径）能解锁三个闸门」 | **❌ 撤回** | 两个闸门的打断源**不是计数**而是 `Missing` 事件 ⇒ M1 对它们无效。且会让 `soak-runner` 的验收判据（`soak.rs:1021`）漏掉真实缺帧 |
| 「M2：队列满时丢队首」 | **⚠️ 部分成立** | ① `PlayoutHandle` **只持有 `Sender`**（`runtime.rs:3024`），`try_push` 里**够不到队首**，方案不可实现；② 反例：弹掉队首后下一拍仍可能 `Missing`；③ guardA 式代价（7×）不能只靠"触发阈值不同"排除 |

## 4. 修订后的诊断与修复路径

### P0（先测量，零行为改动）—— 把三条线分开计数

在三个写入点各加一个**进程内**计数（不进 `StreamStats`，wire schema 冻结；先例 `depth_drops`）：

| 计数 | 位置 | 回答什么 |
|---|---|---|
| `schedule_slip` | `runtime.rs:4981` 的 missed 路径 | 播放线程节拍是否真的在超时（**A 线**） |
| `queue_reject` | `runtime.rs:3099` `try_push` 失败 | 满队列拒收是否真的在发生（**B 线**，v1 从未直接观测到） |
| `cursor_catchup` | `runtime.rs:5500` 追赶分支 | 追赶记账占多少（**C 线**） |

**跑一次现场，三个数字直接给出各自份额** —— 这是 codex 的核心意见，也是本文档唯一该先做的事。

### P1（按 P0 结果对症）

- **若 `schedule_slip` 为主** ⇒ 治**播放线程节拍**。第一嫌疑是**这个实例是 debug 构建**（`cargo run`，无 `--release`）：debug 下音频管线的耗时可能数倍于 release。**零成本验证：同一场景跑 release 构建**。若 release 下消失，则这不是设计缺陷。
- **若 `queue_reject` 为主** ⇒ 治**队列满**，且必须**由播放线程**在硬上限处调用现有入口 `drop_oldest_due_frames`（`runtime.rs:5401`，它已同步推进播放游标），限定每拍数量、保留目标余量。
- **若 `cursor_catchup` 为主** ⇒ 才轮到讨论追赶记账口径。

### P2（明确不做）

在 P0 数字出来之前**不写任何生产代码**。v1 的教训是：凭现场三个聚合数字反推内部机制，会推出 16 倍这种错误结论。

## 5. codex 审核意见摘要（原文要点）

- 根因链：**部分成立**。"这一帧无法补回"成立，"永久缺口、必然永久自锁"不成立。
- 现场读数**无法证明** 48.8 次/秒都来自队列满；必须直接记录满队列拒收次数。
- 总体建议：**需修订后实施**。必须修订：撤回 16 倍及 3% 推算；实测区分满队列拒收 / 序号缺口 / 错过播放拍；保留真实缺帧的验收口径；让修复动作同步处理播放游标；分别验证三个闸门及 guardA 式代价。
