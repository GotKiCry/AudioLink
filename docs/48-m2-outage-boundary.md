# M2 断网自愈边界（拔网 10 s 后 ≤ 3 s 恢复）

> 实测日期：2026-09-17 ｜ 环境：Windows 本机回环 + 双向闸门 UDP 中继模拟拔网 ｜ 测试：`core/crates/audiolink-engine/tests/engine/network_outage.rs`

## 1. 验收原文与结论

`docs/05-roadmap.md` 的 M2 验收点写着：**拔网 10 s，恢复后 ≤ 3 s 内重新出声**。

| 拔网时长 | 旧默认（idle 10 s / keep_alive 3 s） | 新默认（idle 30 s / keep_alive 1 s） |
|---|---|---|
| 2 s | — | 恢复 **0.57～0.74 s** |
| 4 s | 恢复 0.60 / 3.42 / 3.31 s（**双峰**） | 恢复 **0.90～1.13 s** |
| 10 s | **完全不恢复**：两侧会话表里对端都被移除 | 恢复 **4.24～4.84 s**（连测四次，稳定） |

结论两条：

1. **拔网 10 s 从「会话终结」变成「能自愈」** —— 这是本轮真正的功能改进，靠把 `idle_timeout` 从 10 s 提到 30 s 达成。
2. **但「≤ 3 s 恢复」尚未达标**：10 s 拔网的恢复延迟稳定在 4.2～4.8 s，超出验收预算。缺口已记账（本文件 + 看板），未标 Done。

## 2. 根因：三个数值决定「拔网后还能不能回来」

### 2.1 `idle_timeout` 决定「能不能自愈」

空闲超时一过，QUIC 连接被判死。而引擎的会话循环在读写报错时走 `report_peer_gone()` → `SessionState::Failed`，
**没有**任何重拨/重建路径（`SessionState::Reconnecting` 只在收到对端 `Bye` 帧时进入，见 `runtime.rs` 的 `ControlRequest::Bye` 分支）。
也就是说：插回网线也救不回来。

旧值 10 s 正好卡在验收那条线上 —— 拔网 10 s 一到，连接先死，测试里观察到的就是「两侧 `peers()` 里连对端都没了」。
30 s = 10 s（最长可容忍断网）+ 3 s（恢复预算）再留 2 倍余量，同时给移动网络的切换/弱信号留喘息。

### 2.2 `keep_alive` 决定「插回后多久被点亮」

拔网期间没有任何包能出去；插回后链路要等**下一次保活探测**才被重新点亮，于是恢复延迟的上界就是保活间隔本身。
旧值 3 s 时实测恢复延迟呈**双峰**（597 / 3417 / 3310 ms），两个峰之间的距离正是 3 s —— 插回的时机落在保活周期的哪个相位上，决定走哪个峰。
降到 1 s 后，4 s 拔网的恢复延迟稳定在 1 s 附近。

### 2.3 恢复延迟随断网时长增长：PTO 指数退避

10 s 拔网的 4.5 s 不是抖动，是**确定性**的：连测四次为 4415 / 4726 / 4546 / 4237 ms。
这是 QUIC 的 PTO（探测超时）指数退避特征 —— 静默越久，下一次探测排得越晚：

| 拔网 | 下一次探测落点 |
|---|---|
| 2 s | 0.57 s |
| 4 s | 0.90 s |
| 10 s | 4.5 s |

换句话说：**光靠链路层，10 s 拔网不可能在 3 s 内回来**。要达标必须让应用层参与（见 §5）。

> ⚠️ **第 72 轮更正**：上面这句结论已被实测推翻 —— 慢的从来不是链路，是数据面。见 §2.4。

## 2.4 第 72 轮再测量：锅不在链路层（推翻 §2.3 的结论）

§2.3 把 4.5 s 归给 PTO 指数退避，并由此推出「光靠链路层不可能在 3 s 内回来」。第 72 轮给
`network_outage.rs` 的闸门中继加了三个读数（上行/回程分方向计数、音频包到达计数、上行速率逐格采样），
上面那个结论**站不住**：

```text
[outage-diag] 拔网 10000 ms：到达中继的上行音频包 拔网前 9 → 1 s 后 28 → 拔网结束 36
              · 插回后回程首个包 196~326 ms · 上行音频数据报 4086~4273 ms · 声音恢复 4546~4820 ms
[outage-diag] 插回后每 500 ms 的上行包数：[0, 0, 0, 0, 0, 0, 0, 0, 502, 27, 30, 25]
```

三条读数各回答一个问题：

1. **回程首个包 196~326 ms** —— 回程（对端方向来的包）在插回后不到 0.4 s 就有包通过。回程包只有在
   对端**收到上行包并回应**之后才可能出现，所以「链路 3 s 内回不来」被这张表直接否掉：
   **链路 0.3 s 就通了**。
2. **上行速率 `[0×8, 502, 27, 30, 25]`** —— 插回后整整 **4 s**，上行方向**一个包都没有**（含控制帧与保活），
   然后一个采样格内涌出 **502 个**，再回落到 25~30 个/0.5 s（≈50~60 pps，正是音频帧率）。
   502 ≈ 10 s × 50 pps —— 那是**拔网期间积压的全部音频被一次性放出**。
3. **声音恢复 4.5 s ≈ 上行恢复 4.1 s + 0.4 s** —— 后 0.4 s 是抖动缓冲重新填满的代价，属正常。

真正的形状是：**链路早就通了，发送侧的 QUIC 传输却挂着不动，一直等到某个退避定时器到期，
才把积压一次性吐出来**。这不是「路径不可用」，而是「应用与 QUIC 之间缺一条主动恢复路径」——
`report_peer_gone` 把会话直接标成 `SessionState::Failed`（`runtime.rs`，模块文档里也写明
「插回网线也救不回来」），运行时**没有任何重拨/重建路径**。

**方法论上记一笔**：§2.3 的推理并不荒谬（恢复延迟确实随断网时长增长，看着就像退避），
但它只解释了「为什么慢」，没有验证「**谁**在慢」。而一个「插回后 4 s 内上行 0 包」的读数，
就能把链路层与数据面干净地分开。**先加读数，再谈根因。**

## 3. 代码改动

`core/crates/audiolink-engine/src/runtime.rs`：

- `EngineConfig` 新增两个字段并给出默认常量：`idle_timeout`（`DEFAULT_IDLE_TIMEOUT` = 30 s）、`keep_alive`（`DEFAULT_KEEP_ALIVE` = 1 s）；
- 新增 `EngineConfig::with_link_timeouts(idle_timeout, keep_alive)`（成对覆盖 —— 这两个值只有一起看才有意义）；
- `Engine::start` 里原先**硬编码**的 `idle_timeout_ms: 10_000` / `keep_alive_ms: 3_000` 改为读配置；
- `Duration` → QUIC 毫秒字段统一走 `quic_ms()`（0 = 关闭该机制，与 `EndpointConfig` 语义一致）。

可注入的意义不只是测试：移动网络的切换/弱信号场景需要比桌面更大的空闲余量，写死等于所有设备一样。

## 4. 判据陷阱：别把「通道积压」当成「恢复」

第一版判据是「播放回调里出现非静音样本」，结果插回网线后 **1.1 µs** 就报「恢复」了。
真相是：播放回调走无界通道，拔网期间没人消费，通道里堆着**拔网之前**写进去的样本，插回后一读就中。

修正后的判据有三条，缺一不可：

1. 播放端记录 `(写入时刻, 样本)`，「恢复」必须由一个**晚于插回时刻**的非静音样本证明；
2. 必须先证明**拔网期间真的安静了**（缓冲 60 ms，给到 400 ms 余量后仍无新的非静音回调）；
3. 恢复后要**持续**出声（2 s 窗口内 ≥ 20 个非静音回调），而不是把积压一口气吐完就哑。

另外还有一处测量 bug 值得记：持续性窗口最初从 `restore_at` 起算，而恢复本身可能晚于它 —— 窗口早就过期，测出来恒为 0。

## 5. 剩余缺口与候选方案（未实施）

目标：把 10 s 拔网的恢复延迟从 4.5 s 压到 3 s 以内。候选方案按性价比排序：

1. **应用层主动探活**（最小改动）：恢复期不依赖 QUIC 的 PTO 节奏，由应用层按固定节拍（如 200 ms）发控制层 `PING`/心跳，插回后第一时间点亮路径。
   需要先确认一件事：发流期间音频数据报一直在往 QUIC 塞，为什么没起到同样作用（怀疑发送缓冲在不可达时被塞满，新数据进不去）—— 这是下一步的验证点。
2. **接上 FR-27 的重连状态机**（最彻底）：`session.rs` 里 `Reconnecting` / `ReconnectOk` 的迁移表已经写好，但运行时没有实现拨号重连，
   断链仍然直接进 `Failed`。接上它以后，「拔网 10 s」就只是「重连一次」，恢复时间由退避表决定、可控。
3. **调整 QUIC 的探测参数**：`TransportConfig` 层面（`initial_rtt` / 拥塞控制）能加快探测，但属于与标准实现博弈，收益不确定。
4. **改验收数字**（不推荐，需产品确认）：把验收改成「拔网 10 s 后 ≤ 5 s 恢复」。当前行为可以满足，但那等于承认断网恢复能力弱于设计预期。
5. ~~**（第 72 轮）先用方案 1 做一次对照实验**~~ ✅ **已做，方案 1 被否证** —— 见下节。

### 5.1 对照实验（第 73–74 轮）：方案 1 无效，直接上方案 2

给 `run_outage` 加了一个可选探活钩子：拔网期间由**应用层**每 200 ms 调 `Engine::broadcast_epoch(200)`
投喂一个控制帧（只动测试 helper，**没碰产品代码**）。同一天、同机器、背靠背对比：

```text
基线（无投喂）：上行速率 [0, 0, 0, 0, 0, 0, 0, 0, 544, 28, 27] · 声音恢复 5081 ms
有投喂（200 ms）：上行速率 [0, 0, 0, 0, 0, 0, 0, 0, 0, 552, 27] · 声音恢复 5461 ms
                   投喂发出 49 次 · 被引擎接受 49 次
```

**49 次投喂全部「被接受」，但静默期的上行包数仍然是 0。** 也就是说：应用层把数据交给了 QUIC 的发送队列，
而传输层**一个包都没往外发** —— 静默 9 格（4.5 s）与基线 8 格一致，恢复反而更晚 380 ms（属噪声量级，
但足以否掉「投喂能加速」这个假设）。

结论：**方案 1 无效**。缺口不是「应用没投喂」，而是**传输层在长退避里挂死**，连新投喂的数据都不触发发送尝试。
于是只剩方案 2：接上 FR-27 的重连状态机 —— `report_peer_gone` 之后**主动重建连接**，而不是把会话标成
`Failed` 就结束（`session.rs` 里 `Reconnecting` / `ReconnectOk` 的迁移表早就写好了，缺的是运行时实现）。

这条实验的价值在于**低成本排掉一条路**：它没有改一行产品代码，却把「要不要在探活上继续投入」一次答清。
**先做能排他的实验，再动架构。**

```text

```
