# M2 自适应抖动深度与有界重排

日期：2026-09-16

## 1. 交付范围

本阶段把固定 40 ms 开播门槛升级为接收侧三档控制器：

- 目标深度为 20 / 40 / 60 ms（20 ms Opus 帧下为 1 / 2 / 3 帧），默认 40 ms；
- 每秒用接收数据报到达间隔抖动 P95 决策：`<= 5 ms` 目标 20 ms，`<= 20 ms` 目标 40 ms，更高则目标 60 ms；
- 新增欠载立即升一档；降档必须连续稳定 30 个 1 Hz 窗口，且每次只降一档；
- 升档按当前实际水位缺口写入有界静音并保持播放序号，最多等待目标帧数（60 ms）。即使网络中断，也不会无限冻结播放时间轴；
- 降档时若队列确有多余帧，明确丢弃最旧帧并计入 `late_drops`，使实际延迟随目标下降；
- 只有 60 ms 档允许最多等待一个帧周期修复乱序。待排序包最多 3 个；超时交给现有 PCM 丢包掩盖；重复、迟到、`u32` 回绕和大序号跳变都有明确处理。

播放线程可在欠载发生时直接升档。1 Hz 控制器用原子比较交换发布结果，不能用旧决策覆盖这次即时升档。

## 2. 遥测口径

`record_received` 在数据报进入乱序窗时记账，因此真实接收码率不会因等待或迟到丢弃而少算。`lost` / `plc` 在乱序截止后由连续序号接收器确认，乱序窗自身丢弃的重复或过期包进入 `late_drops`。

`buffer_level_us` 仍表示已解码、尚未被播放线程取走的 PCM 帧数乘帧长，不包含 AudioTrack 内部缓冲。目标深度没有新增协议字段；当前实际水位仍是跨端可比较的事实来源。

## 3. 自动回归

引擎测试覆盖以下新增行为：

| 场景 | 断言 |
|---|---|
| `0, 2, 1` 乱序 | 60 ms 档在 Opus 解码前恢复为 `0, 1, 2`，不触发 PLC |
| `0, 2` 后等待 20 ms | 截止时释放 2，接收器为 1 生成 PCM 掩盖，随后到达的 1 计迟到 |
| 序号回绕 | `MAX, 1, 0` 恢复为 `MAX, 0, 1` |
| 深度控制 | 升档立即、稳定 30 秒后逐档下降、阈值映射正确 |
| 有界重缓冲 | 按实际水位缺口等待，网络不补包时最多 3 拍后恢复时钟 |
| 降档 | 只丢真实多余深度，队列已经偏浅时不再额外丢帧 |
| 发布竞态 | 控制器旧值不能覆盖播放线程的并发升档 |

`cargo test -p audiolink-engine --tests` 通过 95 个单元测试和 10 个集成测试；目标模块 Clippy 以 `-D warnings` 通过。

## 5. 后续
